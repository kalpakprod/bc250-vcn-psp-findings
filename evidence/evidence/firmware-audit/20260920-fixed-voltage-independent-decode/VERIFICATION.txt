## CONTRADICTED prior claims (the finding)
C1  prior label "enable test: cmp Setup+0x1c9 vs 0 selects Setup mV vs default 900" asserted at RVA 0x30A.
    Decoded 0x30A: `push 0x21` (register index) - not a compare.
    The enable test decodes at 0x30F: `cmp BYTE PTR [ebp+0x51],bl` (bl==0 from `xor ebx,ebx` @0x27C).
    The same RVA 0x30A is also labelled "VCORE write targets register index 0x21", which is correct.
C2  prior label "write helper reads a u16 little-endian value from [edi]" asserted at RVA 0x709.
    Decoded 0x709: `movzx eax,BYTE PTR [edi]`. The second byte is read at 0x714 (`movzx eax,BYTE PTR [edi+0x1]`)
    and staged to mailbox register 0x71. Net effect (2-byte little-endian value at 0x70/0x71) is real,
    the labelled instruction is a byte read.

## Confirmed by independent decode (prior report stands)
defaults Setup+0x1c9/0x1cd = 0 (bl after `xor ebx,ebx`); +0x1ca/+0x1ce = 0x384 (900) via `mov esi,0x384`;
+0x1cc/+0x1d0 = 2; loadline table {0,20,30,40,50,60} at [ebp+0x60..0x6a] indexed by the Setup byte and
written to register 0x28; mV written to register 0x21 (disabled path: VCORE reuses esi=0x384, GFX writes
an explicit 0x384 immediate); register 0x23 <- 0; register 0xF0 read-modify-write of bit 0x30
(set when Fix Voltage enabled, `and 0xffcf` when disabled) with the read helper 0x653 (0x63<-0x83,
returns mailbox 0xB0/0xB1); helper 0x4D2 writes 0xC7 <- 0xEA0B/0xEA8B and 0xC5 <- 0x0B/0x08 with the
caller's argument order (0x0B when loadline==2, else 0x08); write helper 0x6ED stages 0x65<-0xC0,
0x66<-register, 0x70<-byte0, 0x71<-byte1, 0x63<-3, 0x60<-0xC0, polls status bit 0x40 with <=10 retries
and writes 0x60<-8; transport ports 0x2E/0x2F with the 0x87,0x87 unlock and mailbox 0xA20 (command),
0xA21 (index), 0xA22 (value); both modules locate the PEI Read-Only Variable2 PPI GUID
2AB86EF5-ECB5-4134-B556-3854CA1FE1B4 (bytes verified at the pushed VAs 0x9ED341C / 0x9ED42B4) through a
5-argument indirect call at [*(PeiServices)+0x20] and then call the returned interface slot +0x00 with the
0x1D3-byte Setup variable. ISL95712: defaults 0 / 0x1E(1.35 V), enabled path 0xDF<-stored enum then OR bit 0,
disabled path 0xDF<-0x1E then clear bit 0; both branches also write register 0xDE; follow-up helper stages
0x65<-0x9E, 0x66<-0xDE, 0x63<-0x82, 0x60<-0xC0.

## Boundaries / unrun
- "LocatePpi at PEI_SERVICES+0x20" remains an inference from the argument shape: the decoded call is a
  5-argument indirect call through [*(PeiServices)+0x20] with a PPI GUID; the vendor table layout at that
  offset is not established by these two modules (edk2 numbering would place LocatePpi at +0x08).
- This scan enumerates outer FFS files with a first-level PE32/TE section only. Images inside compressed or
  GUIDed sections and nested FVs (e.g. CpuDxe, a nested GUIDed PE32 at fv_base 0x10) are not enumerated, so
  the prior "exactly three consumers including CpuDxe" statement is neither re-derived nor contradicted.
- FFS header checksum fields in these volumes do not validate under the edk2 rule (0xAA placeholders), so
  file selection used GUID + type + state + exact section-chain fit plus payload-hash equality with the
  pinned census record.
- Runtime PEI dispatch, the mailbox chip, PMBus-style register semantics, physical rail identity and any
  applied voltage remain unverified. No voltage value is recommended and no hardware action occurred.
