# Цепочка верификации $PS1-блобов и вердикт по D3-B2

## Вердикт по D3-B2 (критический)

- Вердикт: блобы 0x24/0x45 из флеша НЕ проходят через загрузчик контейнера fn@0x13468; их верификацию выполняет PSP-загрузчик супервизора вне контейнера, и блобы подписаны RSA-2048.
- Хвост гаскета и политики — ровно 0x100 байт = 256 байт = RSA-2048 подпись; прежнее «хвост маловат для RSA» опровергнуто (0x100 байт — это в точности размер подписи RSA-2048).
- Оба блоба несут идентификатор ключа `96ea7cfe...` по смещению конверта +0x38; тот же kid присутствует в key database `$KDB` записи каталога 0x50 этого же образа (8 ключей, e=65537, 2048 бит).
- Независимый прогон psptool по родственной прошивке BC-250 (Robin5/Robin3, те же адреса/размеры гаскета) помечает SEC_GASKET~0x24 и TOS_SECURITY_POLICY~0x45 как `signed(96EA), verified`.
- Следствие: D3-B2 с непереподписанными телами будет отвергнут при загрузке; риск — отказ PSP грузить гаскет на cold boot (деградация или кирпич), а не тихий игнор.
- Вывод: шить D3-B2 на железо нельзя; путь к цели — неподписанные поверхности (APCB/DFG, checksum-only) либо рантайм-инъекция через mailbox (см. «Обход»).

## Конверт $PS1 — что проверяется

- Поля конверта: sigtype u32@+0x34 (0 → подпись 0x100, 2 → 0x200), rom_size u32@+0x6C (полный размер блоба), kid u128@+0x38.
- У гаскета @0x982000: sigtype=0, rom_size=0x2E50, подпись = последние 0x100 байт (0x2D50..0x2E50); у политики @0x9CA400: sigtype=0, rom_size=0x6E0, подпись = 0x5E0..0x6E0.
- Подписанное сообщение — конверт+тело до подписи; пересчёт без приватного ключа AMD невозможен.
- Каталожный fletcher32 покрывает только сам каталог, не блобы; репоинт записей 0x24/0x45 с пересчётом fletcher32 проходит проверку каталога, но не подпись блоба.
- Оффлайн-воспроизведение RSA-verify в рамках фазы не удалось (схема/раскладка $KDB-модуля отличается от текстового PKCS#1; инструменты `c1_sigverify.py`, `c1_rsa_deep.py`, `c1_rsa_final.py` зафиксировали kid-совпадение и провал brute) — это открытая техническая точка, не влияющая на вердикт: наличие подписи и её проверяемость внешним psptool подтверждены.

## fn@0x13468 — загрузчик $PS1-блобов контейнера

- Единственный вызывающий — arm 0xC0DA командного диспатчера mailbox (сырой BL-скан по каждому полуслову: других вызывающих нет, `evidence/c1_registry.txt`).
- Аргумент r0 — дескриптор команды: `[r8]`=источник-стрим, `[r8+4]`=указатель ожидания 0x20 байт, `[r8+8]`=байт типа (регистрируется в таблице слотов).
- Порядок: svc 0x5e (lock) → стрим-ридер fn@0x6800 (svc 0x6b/0x8b) → проверка магии слов {0x9000, 0x7F} → svc 0x90 (alloc 0x1000) → fn@0xd1fc (верификатор) → два memcmp → регистрация слота в 16-слотовой таблице @0xE4E538.
- memcmp#1: 0x20 байт результата fn@0xd1fc против ожидания по указателю `[r8+4]` из сообщения mailbox.
- memcmp#2: 0x40 байт начала тела блоба (base+0x100) против {0x20 байт из RAM @0xE25814 + 0x20 нулей} (fn@0x1628 — memset-0).
- Провал — чистый код ошибки (0x80000600 / 0xFFFF000x) без halt; слот не регистрируется.
- Внутренний загрузочный путь (fn@0x4914 → fn@0x13628 → fn@0x16658 → fn@0x660c) fn@0x13468 не вызывает; гаскет 0x24 и политика 0x45 из флеша этим загрузчиком не грузятся (тело гаскета начинается со счётчика групп 5, а не с токена — memcmp#2 непроходим для стокового блоба).
- fn@0xd1fc — полный $PS1-верификатор: парсинг конверта, sigtype@+0x34 → размер подписи 0x20/0x200, kid memcmp 0x10 байт против RAM 0xE18420, выборка ключа fn@0x8b5c, аппаратный crypto svc 0x87, SHA-256 0x20/0x30 (`evidence/c1_d1fc.txt`).

## RAM @0xE25814 — источник ожидания memcmp#2

- Литерал 0xE25814 встречается ровно в трёх точках контейнера: 0x13538 (загрузчик) и 0x3560/0x3586 (fn@0x3528).
- fn@0x3528 — обработчик arm 0xC0C4 диспатчера (mailbox-команда; единственный вызывающий): one-shot флаг @0xE188C0, fn@0x5fa0 (крипто-вывод с ключами @0xE17964/@0xE179B2), затем memcpy 0x20 байт из 0xE25814 в тело создаваемого конверта (+0x100) и size-поле 0x40.
- Интерпретация: 0xE25814 — per-boot криптотокен, устанавливаемый командой arm 0xC0C4; fn@0x3528 одновременно строит RAM-конверт, чьё тело начинается с токена, что гарантирует прохождение memcmp#2 загрузчика.
- Смежные структуры той же зоны безопасности: 0xE2547C, 0xE25794, 0xE257D5, 0xE25834; источник ключей — 0xE179xx (вне контейнера, фьюз/OTP-класс), не перепрошиваемый блоб.
- Следствие: ожидание memcmp#2 не берётся из каталога и не пересчитывается на стороне хоста без команды 0xC0C4; TOCTOU между установкой токена и загрузкой отсутствует.

## Реестр групп @0xE5CBDC и таблица @0xE4E538

- Реестр 0xE5CBDC внутри контейнера только читается (fn@0x1167c getter: точки 0x218a, 0xa512/0xa534/0xa548 в донорском fn@0xa4e4, 0xfebe в fn@0xfeac; плюс литерал секвенсера @0x2164 для лог-контекста).
- Писателей 0xE5CBDC в контейнере нет — реестр наполняет супервизор после загрузки и проверки гаскета/политики.
- Донорский обработчик fn@0xa4e4 (группы 0x206/0x210/0x208) читает пары из реестра, т.е. применяет только группы уже верифицированного блоба.
- Таблица 16 слотов @0xE4E538 — регистрация mailbox-загруженных блобов (fn@0x13468 запись, fn@0x13680/fn@0x136b0 очистка по arm 0xC0E2); отдельная от реестра.
- Регистратор fn@0x11560 (BL из fn@0xe7a8) пишет таблицу ключей @0xE97A88, не реестр групп.

## Обход (если проверка есть — она есть)

- (а) Каталожная запись: ожидание подписи не берётся из каталога; каталог задаёт только адрес/размер; репоинт не отключает проверку.
- (б) TOCTOU: реестр строится из тела блоба после проверки супервизором; внутри контейнера повторной проверки нет, но непроверенный блоб в PSP-память не попадает — TOCTOU внутри контейнера не открывается.
- (в) Self-signed ключ: записи каталога 0x50/0x51 ($KDB) сами являются $PS1-подписанными блобами; корень доверия — фьюзы. Подмена $KDB не помогает.
- (г) Mailbox-путь (жизнеспособная альтернатива): arm 0xC0C4 (fn@0x3528 — установка токена 0xE25814 + сборка конверта) и arm 0xC0DA (fn@0x13468 — загрузка $PS1-блоба) образуют двухкомандный канал инъекции произвольного блоба групп: проверка = токен + хеш по указателю `[r8+4]` из самого сообщения; RSA-подпись хвоста тут не проверяется. Если актор хоста/супервизора может выдавать эти команды с выбранным дескриптором, кастомный блоб групп грузится и регистрируется в @0xE4E538. Открытый вопрос: перестраивает ли супервизор реестр 0xE5CBDC из mailbox-загруженного блоба (писателей реестра в контейнере нет).
- (д) Mailbox-применение «одной командой»: fn@0x2008(type) — обёртка «применить любой тип с гейтами», но все шесть вызывающих (fn@0x1ac4, fn@0xf8f4, fn@0xfe04, fn@0x10044×3) передают фиксированные типы; arm с type из сообщения не найден. Пары {E810,6} в стоке нет ни в одной группе подписанных блобов — применить её рантайм-командой без инъекции блоба (путь г) нельзя.

## Рекомендация

- Заморозить D3-B2 как неподписываемый; не прошивать.
- Основной путь VCN-разблокировки — неподписанная поверхность APCB (DFG/`03 17`-таблицы, checksum-only, per VULN-BC250-002) и APCB-часть D3.
- Второй путь — рантайм: добиться выдачи mailbox-команд 0xC0C4→0xC0DA (двухшаговая инъекция блоба групп) из кода, имеющего доступ к C2PMSG/PSP-mailbox; далее применитель fn@0x2008/fn@0x2178 применит группы через реестр, если тот перестроится.
- Открытые точки: точная раскладка $KDB-модуля для оффлайн-verify; перестройка реестра из mailbox-блобов; соответствие номеров mailbox-команд arm-ам 0xC0C4/0xC0DA (требует трассировки головки диспатчера).
