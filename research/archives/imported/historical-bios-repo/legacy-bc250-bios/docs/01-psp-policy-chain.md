# Цепочка применения PSP-политик

## Образ и каталог

- Сток-образ 16 MiB содержит PSP-каталог по адресу 0x8E0000: 19 записей формата «тип, размер, адрес».
- Запись 0x24 — гаскет: блоб по адресу 0x982000, размер 0x2E50.
- Запись 0x28 — TOS-контейнер: блоб по адресу 0x984F00, размер 0x1A790; код Thumb-2 начинается со смещения 0x100 от начала блоба.
- Запись 0x45 — TOS_SECURITY_POLICY: блоб по адресу 0x9CA400, размер 0x6E0.
- Заголовок каждого блоба формата $PS1 содержит: счётчик групп по смещению +0x100, массив описаний групп, пары «адрес → значение».
- Заголовок контейнера 0x28: магия $PS1 по +0x10, размер 0x1A570 по +0x14, поля +0x58..+0x7C (включая «RBN » по +0x64 и 0x1A770 по +0x6C); полей entry-point нет.
- Первые 0x100 байта блоба не содержат кода (ARM и Thumb декодирование дают только нули/данные); хвост за последней инструкцией — 0x22 байта данных.

## Загрузчик блобов

- fn@0x13468 загружает и верифицирует блобы формата $PS1: svc 0x90 выделяет память, svc 0x88/0x68 читает поток, fn@0xd1fc проверяет подпись (RSA-2048, SHA-256, svc 0x87).
- Смещение головы: 0x13468; прежнее «fn@0x1346a» — декод со сдвигом на 2 байта (0x1346A — вторая полуинструкция push.w).
- Верификация сравнивает 0x20/0x40 байт с ожиданием из RAM по адресу 0xE25814; провал возвращает ошибку без остановки.
- Загруженный блоб регистрируется в таблице из 16 слотов по адресу 0xE4E538.
- Вызов загрузчика: arm диспатчера 0xC0DA (`bl 0x13468`) — загрузчик вызывается командой mailbox.

## Реестр групп

- fn@0x1167c(type) возвращает из реестра по адресу 0xE5CBDC счётчик и массив пар группы заданного типа; отсутствие группы возвращает ненулевой статус.
- Пользователи реестра: fn@0xfeac, fn@0x2178, fn@0xa4e4.

## Интерпретаторы

- fn@0x2178(type) — универсальный примитив «применить группу по типу»; все применители контейнера идут через него:
  - типы (0x203, 0x217) — прямая запись значения по адресу пары;
  - остальные типы — svc 0x7c(адрес, значение, 4).
- Полный список вызывающих fn@0x2178 (13 точек, сырой скан bl):
  - fn@0x1ef4 — группа 0x211;
  - fn@0x2008(type) — обёртка «применить любой тип с гейтами»;
  - fn@0x2084 — группа 0x215;
  - fn@0x20d4 — секвенсер, шесть типов;
  - fn@0xcaa4 — группа 0x214;
  - fn@0xcdbc — группа 0x290;
  - fn@0xe1f6 — группа 0x221;
  - fn@0xeb8e — группа 0x222 (затем продолжение с типом 0x284).
- fn@0xfeac(type) — второй, параллельный интерпретатор:
  - тип 0x281 — прямая запись значения по адресу пары;
  - типы (0x280, 0x282, 0x284) — svc 0x7c(адрес, значение, 4);
  - все остальные типы — svc 0x7c(адрес, 0, 4); значение зануляется.
- Вызывающий fn@0xfeac внутри контейнера отсутствует: сырые сканы bl/blx/b.w на любом полусловном смещении, окно ±0x10 и вся область 0xFE60..0xFF40 дают ноль точек.
- Группы 0x280-семейства применяются только интерпретатором fn@0xfeac; внутренние применители их не касаются.
- Следствие: в стоке применение 0x280-семейства либо выполняется вызывающим вне контейнера, либо не выполняется вовсе.

## Секвенсер и обёртки

- fn@0x20d4 — секвенсер; прежнее «fn@0x20d8» — голова со сдвигом 4 байта (0x20D4: ldr r1,[pc,#0x94]; movs r0,#1; push {...}).
- fn@0x20d4 записывает байт-флаг «выполнено» и применяет через fn@0x2178 фиксированный порядок типов: 0x201, 0x205, 0x203, 0x20A, 0x20B, 0x210.
- Гейты секвенсера: fn@0x9f5c, байт-флаг из литерал-пула, fn@0x88fc == 0x100.
- Отсутствующая группа возвращает успех; секвенсер переносит сток-гаскет без групп (0x205, 0x20A, 0x20B).
- Вызов секвенсера: arm диспатчера 0xC344 (`bl 0x20d4`) — команда mailbox.
- fn@0x2008(type) — обёртка: байт-флаг, спец-путь для 0x225 (svc 0x8b2c/0x17148/0xf728), гейт fn@0x88fc, затем fn@0x2178(type).
- fn@0xa4e4 — обработчик донорского набора групп (0x206, 0x210, 0x208) с гейтами по состоянию RAM+0x41C и байт-флагу; голова 0xa4e4 (прежнее «0xa4e6» — сдвиг 2 байта).
- Вызов донорского обработчика: 0x9606 внутри fn@0x946c; fn@0x946c вызывается arm'ом диспатчера 0xBF6E.
- fn@0x1ef4 — применитель 0x211; вызывается из fn@0xca78 ← arm диспатчера 0xC632.
- fn@0xcaa4 — применитель 0x214 с гейтами секвенсера; вызывается arm'ом 0xC638 и из fn@0xfe04.
- fn@0x1ec4 — применитель 10 фиксированных пар по байт-флагу; вызывается arm'ом 0xC2B0 через трамплин 0x20D0.

## Полный применитель fn@0xfe04

- fn@0xfe04 — «применить всё»; вызывается arm'ом диспатчера 0xC1BC.
- Последовательность: fn@0x10f0c → fn@0x10bf8 → fn@0x9970 → гейт fn@0x8f20(1) → fn@0xfdc8 (константные записи) → fn@0xfd00(9) → fn@0xfd00(0xA) → гейт → fn@0xcaa4 (0x214) → fn@0x2008(0x225) → fn@0x140ac → гейт → fn@0x2084 (0x215).
- fn@0x140ac дополнительно вызывается из оркестратор-шага fn@0xf788 (точка 0xF8F8) и fn@0x10044 (0x10096).

## Пер-типовая инфраструктура

- fn@0x10bf8, fn@0x10f30, fn@0xff30 — обходчики фиксированной таблицы из 0x32 u16-типов; таблицы в RAM: 0xE17BEE, 0xE17B26, 0xE17B8A.
- Гейты обхода: fn@0x122bc — skip-лист типов (0x0C, 0x0E, 0x0F, 0x10, 0x12, 0x22, 0x23, 0x28, 0x29); fn@0x9cf0 — проверка пер-типового состояния.
- fn@0x504c(type) — пер-типовая запись в слоты: база 0x09000808 + type*0x1000 (три/четыре слова, значения частично из fn@0x8ac8).
- fn@0xff30 — очистка пер-типовых слотов: базы 0x09000914 + type*0x1000, 0x09000930 + type*0x1000, 0x09000B80 + type*0x1000; вызывается из fn@0x660c (точка 0x6672).
- fn@0x10f30 — запись пары значений (из struct+0x14) в слоты 0x09000808 + type*0x1000 и +4; вызывается из fn@0x660c (точка 0x663E).

## Загрузочная цепочка

- fn@0x4914 выбирает стадию загрузки: стадия 1 запускает fn@0x13628 напрямую либо через гейт fn@0x78e0; вызывающий — 0x5C44 (главный цикл состояний).
- fn@0x13628: fn@0x11e34 → fn@0x16658 → fn@0x660c; затем состояние 3 в +0x238 и снятие бита 30 поля +0x998.
- fn@0x16658 — оркестратор обработки: строит три буфера, вызывает (0x10fac, 0x83e0, 0x16340, 0xf788, 0xaed4, 0x16aa4).
- fn@0x660c: svc-подготовка → fn@0x10f30 (пер-типовая запись) → гейт fn@0x62b8 → fn@0xff30 (пер-типовая очистка).
- Крипто-верификатор fn@0xd1fc вызывается из шести точек: (0xC034, 0xDCAC, 0xEAC6, 0x13520, 0x169D8, 0x16A42).

## Командный диспатчер

- Голова диспатчера — fn@0xBA98 (push.w 11 регистров): контекст r4, команда = слово `[r4]`; выбор arm — бинарное дерево cmp/beq/bgt c 0xBB10 + tbb-таблицы.
- Точки сравнения головы: 0x106e, 0x1030, 0x1014, 0x1007, 0x1001, база sl (литерал 0xFFFF000F @0xBD28, минус 5), литерал 0xFFFEF005 @0xBD2C; дальше цепочки по r1 = cmd−0x106e (таблицы b1_emul2.txt).
- Диспатчер — единственный вход применителей политик; карта «команда → arm → действие» (полная — evidence/b1_emul2.txt, b1_cmdmap.txt):

| Команда `[r4]` | Arm | Действие |
|---|---|---|
| 0x1033 | 0xC344 | `bl fn@0x20D4` — секвенсер (группы 0x201, 0x205, 0x203, 0x20A, 0x20B, 0x210) |
| 0xFFFF0001 | 0xC1BC | `bl fn@0xFE04` — применить всё |
| 0xFFFF0005 | 0xC1BC | то же (второй вход, через проверку cmd+0xFFFB==0) |
| 0x100C | 0xC0D0 | `bl fn@0x13468` @0xC0DA — $PS1-загрузчик блоба |
| 0x1000 | 0xBF6A | `bl fn@0x946C` @0xBF6E — донор-обработчик (0x9606 → fn@0xA4E4, группы 0x206/0x210/0x208) |
| 0x310F | 0xC630 | `bl fn@0xCA78` @0xC632 → fn@0x1EF4 (группа 0x211) |
| 0x3110 | 0xC638 | `bl fn@0xCAA4` (группа 0x214) |
| 0x1026 | 0xC2B0 | `bl 0x20D0` → fn@0x1EC4 (10 фиксированных пар по байт-флагу) |
| 0x1005 | 0xC022 | `bl fn@0xD1FC` — крипто-верификатор (RSA-2048/SHA-256) |
| 0x1040 | 0xC3B4 | `svc 0x9e` напрямую |
| 0x1001..0x10FF, 0x2001..0x2007, 0x3001..0x3010, 0x3101..0x3133, 0x4003..0x4007, 0x6001..0x6003, 0x7001..0x7002, 0x8001..0x8005 | 0xBF74..0xC7A0 | сервисные arm-ы (полный список в b1_emul2.txt) |

- Все команды вне перечисленных диапазонов попадают в default-выход 0xC7AA (движения нет).
- Командные слова группы 0x210 стока (0x2232C240 … 0xF853C480) НЕ являются командами диспатчера: ни одно слово и ни одна проверенная маска не попадает в arm. Слова — значения пар группы 0x210, применяемые секвенсером через fn@0x2178 как `svc 0x7c(0x0003E814, слово, 4)`.
- Пара-триггер 0x3E810: сток → значение 0, донор → 6 (патч D3-B2); применяется той же командой секвенсера/донор-обработчика как `svc 0x7c(0x0003E810, значение, 4)`.

## Порядок применения групп

- Внутри одной группы пары применяются в порядке описей реестра; реестр наследует порядок описей $PS1-заголовка блоба.
- Между типами порядок задаётся вызывающим: секвенсер fn@0x20d4 — фиксированный список (0x201, 0x205, 0x203, 0x20A, 0x20B, 0x210); fn@0xfe04 — свой внутренний список; одиночные обёртки — по одной группе.
- Конкуренция значений 0x201 против 0x280 внутри контейнера не реализована: семейство 0x280 применяется только интерпретатором fn@0xfeac, у которого внутренних вызывающих нет.

## Внешний вызывающий (поиск в образе)

- Каталог $PSP @0x8E0000: 19 записей; ABL (типы 0x03/0x04) в каталоге отсутствует; blob 0x01 (PSP bootloader, 0xA800) и 0x02 зашифрованы (нет $PS1-заголовка, высокая энтропия).
- Ни один blob образа не содержит абсолютных констант 0x984F00 (адрес контейнера), 0x982000 (гаскет), 0xFEAC/0xBA98 (смещения входов контейнера), 0x8E0000 (база каталога), размеров 0x1A770/0x1A570/0x2E50 (кроме самих заголовков blobs 0x24/0x28).
- Адреса 0x3E810/0x3E814 встречаются ТОЛЬКО в таблицах пар группы 0x210 гаскета (0x24) и TOS_SECURITY_POLICY (0x45) — потребитель этих записей в образе прошивки отсутствует.
- Следствие: супервизор, грузящий контейнер и вызывающий диспатчер fn@0xBA98 командами 0x1033/0xFFFF0001/0x100C/0x1000, живёт в on-die PSP ROM или в зашифрованном bootloader 0x01/0x02; статически из этого образа недостижим.
- Вызывающий fn@0xFEAC: в образе не найден (см. выше); остаётся вызов из on-die ROM/зашифрованного bootloader по абсолютному адресу загруженного контейнера либо мёртвый код.

## Сток-гаскет 0x280/0x281: путь применения

- Обходчик fn@0x10bf8 (шаг полного применителя fn@0xFE04) НЕ применяет пары групп: для каждого типа из 32-элементной runtime-таблицы он делает skip-проверку fn@0x122bc, проверку состояния fn@0x9cf0 и пер-типовую запись слота fn@0x504c (база 0x09000808+type*0x1000).
- Skip-лист fn@0x122bc содержит 0x28 (не 0x280/0x281): типы 0x280/0x281 формально проходят обход, но действие — только запись слота состояния, не применение пар.
- Ни один arm диспатчера и ни один внутренний вызов не передаёт 0x280/0x281 в fn@0xFEAC или fn@0x2178.
- Вывод: значения пар 0x280/0x281 сток-гаскета не применяются внутри контейнера ни по одному пути; применитель — только внешний fn@0xFEAC (вызов недоступен статически) либо не выполняется вовсе.

## D3-B2 (E810→6 в 0x210)

- Значение 6 по адресу 0x3E810 (донор; сток — 0) применяют два пути: команда 0x1033 (секвенсер fn@0x20D4, группа 0x210 — последняя в порядке) и команда 0x1000 (донор-обработчик fn@0x946C → fn@0xA4E4, группы 0x206/0x210/0x208).
- В обоих случаях значение доходит до железа как `svc 0x7c(0x0003E810, 6, 4)` через fn@0x2178 (тип 0x210 — не 0x203/0x217, поэтому svc-путь).
- Слово-команда донора 0x2544C382 по адресу 0x3E814 применится той же командой как `svc 0x7c(0x0003E814, 0x2544C382, 4)`; дополнительные пары донора: 0x1F8A4→0xB, 0x1F820→0x185103.

## Открытые вопросы

- Содержимое фиксированных u16-таблиц типов @RAM (0xE17B26, 0xE17B8A, 0xE17BEE): таблицы заполняются в runtime, статически не читаются; порядок обхода fn@0x10bf8 определяется этими таблицами.
- Источник ожидания подписи в RAM по адресу 0xE25814 неизвестен: фьюзы или подписанное хранилище.
- Потребитель записей 0x3E810/0x3E814 (за пределами образа) и формат командного слова 0x2232C240-семейства (байты 22/24/25/F8, 32..78, C2/C4, 40..82) не идентифицированы: гипотеза «младшие биты = номер команды» картой диспатчера опровергнута, декодер живёт в on-die ROM/зашифрованном bootloader.
