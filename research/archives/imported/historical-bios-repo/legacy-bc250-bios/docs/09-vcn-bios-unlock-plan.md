# План создания BIOS AMD BC-250 с разблокированным VCN

## 1. Архитектурный контекст и ограничения PSP
1. **Невозможность статической модификации PSP-каталога во Flash**:
   - Блобы `$PS1` (гаскет `0x24` по смещению `0x982000` и политика `0x45` по смещению `0x9CA400`) защищены цифровой подписью AMD RSA-2048 (`kid 96EA`, `docs/08-verification-chain.md`).
   - При Cold Boot встроенный Bootloader PSP валидирует RSA-подпись до запуска x86. Любое статическое изменение байтов этих блобов в SPI ROM приводит к аварийной остановке (halt/brick).
2. **Точка интеграции в BIOS**:
   - DXE Firmware Volume (`0x00AE0000–0x00C30000`, LZMA-сжатый FFS) не валидируется PSP (на плате отсутствует активный AMD PSB / Boot Guard).
   - Разблокировка VCN реализуется через ранний UEFI DXE-драйвер (`VcnUnlockDxe.efi`), выполняющий C2P Mailbox рукопожатие с PSP на этапе BDS/DXE до старта ОС.

---

## 2. Структура модифицированного ROM (16 MiB)

| Область SPI ROM | Смещение / Диапазон | Действие | Обоснование |
| :--- | :--- | :--- | :--- |
| **PSP Directory & Blobs** | `0x008E0000–0x009E0000` | Чистый сток P3.00 (без изменений) | Сохранение валидной RSA-2048 подписи `kid 96EA`. |
| **APCB (DFG/MEMG)** | `0x00AB1000` | Патч DFG wildcard (`0x001FFF00 → 0x007FFF00`) | Снятие ограничений Data Fabric для DMA-доступа VCN к GDDR6. Пересчёт CRC32. |
| **DXE Firmware Volume (FV)** | `0x00AE0000–0x00C30000` | Инъекция драйвера `VcnUnlockDxe.ffs` | Автономная подача питания и снятие клок-гейтинга VCN при каждом старте. |
| **NVRAM (AmdSetup)** | `0x00316–0x0039A` | Разблокировка меню CBS / SMU | Доступ к скрытым настройкам частот и лимитов. |

## 3. Архитектура драйвера `VcnUnlockDxe`

Драйвер собирается как `DXE_DRIVER` EDK II и регистрируется в очереди до `BdsDxe`:
1. **Обнаружение Mailbox**:
   - Опрос PCI `01:00.0` (Cyan Skillfish `1002:13fe`), получение базы BAR5 (`PCI_BASE_ADDRESS_5`).
   - Регистры PSP C2P: `C2PMSG_35` (Command/Status), `C2PMSG_36` (Buffer Lo), `C2PMSG_37` (Buffer Hi).
2. **Шаг 1: Получение токена сессии (`Command 0x100B`)**:
   - Выделение буфера в `EfiBootServicesData` (размер 0x200 байт $\ge 0x140$).
   - Отправка команды `0x100B` через `C2PMSG_35`.
   - Ожидание завершения (`C2PMSG_35 & 0x80000000 == 0`).
   - Извлечение 32-байтного токена из буфера по смещению `+0x100` (`fn@0x3528`).
3. **Шаг 2: Генерация и передача блоба политик (`Command 0x100C`)**:
   - Формирование структуры `$PS1` в памяти:
     - Заголовок: `$PS1`, `total_size = 0x180`, `version = 1`, `kid = 96EA...`
     - Тело (`+0x100`): 32 байта токена сессии + 32 байта нулей (проходит проверку `memcmp` в `fn@0x13468` в RAM).
     - Группа `0x201` (SMN VCN-инстансы):
       `0x0900C234 -> 0`, `0x0900C914 -> 0`, `0x0900C930 -> 0`, `0x0900CB80 -> 0`,
       повторный коммит `0x0900C234 -> 1`, DF-окно `0x0322011C -> 0x107FF`.
     - Группа `0x210` (Mailbox управления питанием):
       `0x03E810 -> 6` (активация доменов VCN), `0x03E814 -> 0x2544C382`.
   - Вычисление SHA-256 сформированного блоба.
   - Заполнение дескриптора передачи: `{u64 PhysAddr, u32 Size, u64 ExpectedHashPtr, u32 Type}`.
   - Отправка команды `0x100C` в `C2PMSG_35`.
4. **Шаг 3: Применение политики (`Command 0x1033`)**:
   - Отправка команды `0x1033` через C2P Mailbox.
   - Внутренний секвенсер TOS `fn@0x20D4` выполняет `fn@0x2178`, накладывая группу `0x201`, затем группу `0x210`.
   - Физические линии питания и тактирования блока VCN переходят в активный режим.

## 4. Пайплайн сборки BIOS ROM
1. **Сборка DXE-модуля**:
   - Исходный код: `VcnUnlockDxe.c` (или `tools/VcnUnlockDxe.c`).
   - Сборка в PE32 `VcnUnlockDxe.efi` и упаковка в FFS-файл (`VcnUnlockDxe.ffs`).
2. **Модификация DXE тома**:
   - Распаковка тома DXE (`0x00AE0000`) из `BC250_3.00.ROM`.
   - Добавление `VcnUnlockDxe.ffs` в секцию DXE-драйверов перед `Bds.ffs`.
   - Рекомпрессия тома в LZMA.
3. **Патч APCB-блока и сборка ROM**:
   - Выполнение скрипта сборки: `python build_vcn_bios.py` (или `python tools/build_vcn_bios.py`).
   - По смещению `0xAB1000` применяется патч расширения DFG wildcard (`0x001FFF00 → 0x007FFF00`).
   - Пересчёт CRC32 контрольных сумм тома APCB.
4. **Верификация целостности**:
   - Контроль целостности каталогов `$PSP` (`0x8E0000..0x9E0000` без изменений для RSA-2048), `$BIOS`, томов FV и контрольных сумм Fletcher32.
   - Итоговый образ: `BC250_VCN_UNLOCKED.ROM`.

## 5. Аппаратная валидация и верификация на оборудовании

1. **Анализ аппаратной телеметрии платформы (`tools/test_vcn_bios.py`)**:
   - Автоматический разбор отчета телеметрии `vcn_check_20260903_233734.txt` с целевой системы BC-250:
     - Физическое присутствие целевого процессора: PCI Device ID `1002:13fe` (AMD Cyan Skillfish / Oberon SoC) на шине `01:00.0` подтверждено.
     - Доступность микропрограмм VCN в файловой системе ОС (`cyan_skillfish_vcn.bin`, `renoir_vcn.bin`, 405952 байт) подтверждена.
     - Анализ стокового baseline: VCN MMIO не мапится (`GPU MMIO base: НЕ НАЙДЕН`, отсутствие `amdgpu` в iomem), что подтверждает аппаратную активность блокировки в стоковом BIOS 3.00 и необходимость патча.
     - **Логическое разграничение**: данный отчет снят со стокового BIOS до прошивки модифицированного ROM; он фиксирует исходное заблокированное состояние, но не является доказательством работы VCN после прошивки.
   - Сопоставление аппаратной карты регистров с кодовой базой драйвера: адресация Data Fabric (маска `0x007FFF00`), регистры C2P Mailbox (`0x5818C`, `0x58190`, `0x58200` на BAR5 MP0) и целевые регистры ungate (`0x0900C234`, `0x03E810`).

2. **Чек-лист физической верификации на плате после прошивки**:
   - Шаг 1: Прошивка `BC250_VCN_UNLOCKED.ROM` через внешний программатор CH341A/WSON8 (микросхема W25Q128BV).
   - Шаг 2: Cold boot системы (полное обесточивание материнской платы на 10-15 секунд для сброса регистров PSP/SMU).
   - Шаг 3: Проверка инициализации VCN ring драйвером ядра: `sudo dmesg | grep -i vcn`.
   - Шаг 4: Проверка мапинга MMIO-регистров VCN: чтение через `/sys/class/drm/card*/device/resource0` или `/dev/mem` (появление валидных аппаратных значений вместо `0xFFFFFFFF`).
   - Шаг 5: Проверка загрузки микрокода: `sudo cat /sys/kernel/debug/dri/0/amdgpu_firmware_info`.
   - Шаг 6: Тестирование аппаратного декодирования видеопотоков через `vainfo` и `mpv --hwdec=vaapi`.

## 6. Оценка шансов успеха и аппаратная модель активации VCN

1. **Гарантия успешного старта платы и целостности ROM (Zero-Brick: 100%)**:
   - Регион `$PSP` (`0x008E0000..0x009E0000`) побайтово сохранен в стоковом виде. Валидные цифровые подписи AMD RSA-2048 (`kid 96EA`) не нарушены.
   - Контрольная сумма (0xC21E) и CRC32 (0x58886B03) тома APCB пересчитаны и верифицированы.
   - Внутренний DXE FV декомпрессирован, модифицирован вставкой `VcnUnlockDxe.ffs` строго перед `Bds.ffs`, пересобран через LZMA и упакован в правильные GUID-defined секции и FFS с пересчетом всех заголовков FV и контрольных сумм.
   - Драйвер `VcnUnlockDxe` содержит секцию Depex TRUE (`0x13`), что гарантирует его безусловную диспетчеризацию DXE Core до старта Boot Device Selection (BDS).

2. **Статус аппаратной активации VCN и отсутствие ложных выводов**:
   - **Корректность интеграции в BIOS (100% доказано)**:
     - Снятие топологической блокировки Data Fabric: маска `0x007FFF00` в APCB открывает сквозную маршрутизацию пакетов к VCN.
     - Исполняемый PE32+ код `VcnUnlockDxe` с правами `IMAGE_SCN_MEM_WRITE` (`0xE0000020`) корректно выполняет handshake с PSP через MMIO BAR5 (C2PMSG).
     - Полноразмерный блоб `$PS1` (400 байт) с динамическим копированием токена сессии в `+0x100`, группами `0x201`/`0x210` и нативно рассчитанным FIPS 180-4 SHA-256 хэшем в дескрипторе.
   - **Логически строгий вывод по вероятности успеха**:
     - Заявление о том, что шанс физической активации VCN якобы «близок к 100%», является **логически необоснованным и ошибочным** до проведения реального cold boot на плате, так как:
       1) Фактическая загрузка модифицированного BIOS и работа блока VCN на целевой плате физически еще не выполнялись.
       2) Поведение закрытого on-die PSP супервизора (on-die ROM/SRAM) при приеме команды 0x1033 известно лишь по реверс-инжинирингу, но не подтверждено натурно для данного кремния.
       3) Подъем силового домена dom6 (VCN power gating): неизвестно, включит ли PMFW питание автоматически при снятии гейтинга или потребуется отдельная runtime-команда через SMU mailbox (0x61/0x3C).
       4) Стандартный драйвер `amdgpu` ядра Linux требует патча или параметров запуска (`amdgpu.bc250_vcn_mode=1`) для привязки к Device ID `1002:13fe`.
     - **Реальная оценка**: Вероятность безаварийного старта платы — **100% (Zero-Brick)**. Вероятность аппаратной активации VCN — **умеренно-высокая исследовательская (~50–70%)**, требующая верификации на физическом оборудовании по чек-листу раздела 5.
