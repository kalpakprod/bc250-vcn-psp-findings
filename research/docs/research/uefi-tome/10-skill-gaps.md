# Глава 10. Карта пробелов: софт, скиллы, железо для отладки

Эта глава — честный реестр того, чего тому и проекту
не хватает, с планом закрытия по каждому пункту.
Правило: каждый пробел привязан к свидетельству
(журнал/аудит/решение), а не к ощущению.
Статусы: ОТКРЫТ (ничего нет), ЧАСТИЧНО (есть зачаток),
ЗАКРЫТ (проверяемо сделано — таких здесь нет по определению).

## Часть 1. Софт

### S1. Канал наблюдения за ранней загрузкой (UART/POST-декодер) — ОТКРЫТ

- В чём пробел: ни один «молчащий» рунг (D5–D7, M0/M2full/
  M4/M5/M6) не был локализован: различать «PSP отверг»,
  «ABL упал», «DXE не диспетчится», «висит в колбэке»
  нечем. Рекурсивный аудит называет это «глубочайшей
  причиной отсутствия результата».
- Свидетельство: `docs/research/2026-09-17-campaign-error-audit.md`
  (регистр ошибок, forward tree R0–R4);
  standing rule instrument-first в `memory/project-state.md`.
- План закрытия:
  1. Аппаратно: подпаяться/подключиться к J5 (UART,
     сначала проверить 3.3 В TTL) либо снимать POST
     с TPMS1/LPC пост-картой (см. H1–H2 ниже).
  2. Софтово: скрипт захвата лога + привязка кодов
     к фазам (таблица POST-кодов AGESA/AMI для этой платы —
     отдельный подпункт, сейчас её нет).
  3. Гейт: ни одной флеш-кампании без живого канала
     (правило уже принято — anti-G6/instrument-first).
- Критерий закрытия: захват лога/кодов хотя бы одного
  молчащего рунга с различением PSP/ABL/DXE-фаз.

### S2. Загрузка UEFI Shell на BC250-01 — ОТКРЫТ

- В чём пробел: весь план живой проверки DF/SMN
  после dfprobe-инцидента (решение D17) зависит от
  UEFI-Shell .efi, но сама загрузка Shell на плате
  не построена и не доказана.
- Свидетельство: `memory/decisions.md` D17–D18;
  `docs/action-logs/2026-09-13-pei-vni-hunt.md` (OQ6/OQ7).
- План закрытия:
  1. Собрать минимальный Shell.efi-хелловорлд под EDK II
     (тот же тулчейн, что D5: GCC 16.2.1, X64 RELEASE).
  2. Загрузить с USB через встроенный Boot Manager
     (без перешивки SPI): проверить видимость USB,
     SecureBoot-статус, подпись.
  3. Доказать выполнение (скрин/лог/запись маркера
     в переменную) — только после этого писать
     DF-зонд (S3).
- Критерий закрытия: воспроизводимая загрузка Shell
  с USB с логом на экране/флешке.

### S3. UEFI-Shell зонд DF/SMN (преемник dfprobe) — ОТКРЫТ

- В чём пробел: dfprobe доказал, что DF/SMN из Linux —
  запретная зона даже read-only; безопасный контекст
  (прошивка) без инструмента.
- Свидетельство: кейс 13 главы 07;
  `memory/firmware-audit.md` (G7 HAZARD).
- План закрытия:
  1. После S2: зонд, повторяющий карту чтений dfprobe,
     но из Shell, с инкрементальным порядком
     (по одному адресу, с паузой и логом после каждого).
  2. G7-оговорка вшита в дизайн: открытость DF в Shell
     ТЕСТИРУЕТСЯ (ext-config disable уже отработал
     к моменту Shell), а не предполагается.
  3. Стоп-условие: первый ханг = бит информации
     (адрес известен из лога) + холодный цикл.
- Критерий закрытия: карта «адрес → читается/виснет»
  из Shell для DF-окон и VCN-банка.

### S4. `trace_sec_gasket_executor.py` (путь P1.5a) — ОТКРЫТ

- В чём пробел: первичный путь карты (офлайн-RE
  исполнителя SEC_GASKET type-0x24: диспетч групп,
  requester/client для HWID 12, переходы commit+lock)
  существует только как строка в ранжированном списке.
  Скрипта, Cutter-сессии и модели автомата нет.
- Свидетельство: `docs/research/2026-09-12-unlock-paths-map.md`
  (п. 1 ranked next actions); P1.5a.
- План закрытия:
  1. Собрать корпус ABL/PSP-тел текущего образа
     (адреса/хеши — из `firmware_audit.py`).
  2. Найти парсер type-0x24 (якоря: константы групп,
     HWID 12, строки ошибок) — Cutter + Ghidra,
     паритет двух линз (D19).
  3. Выдать предсказание наблюдаемого внутреннего
     изменения состояния ДО любых попыток хоста.
- Критерий закрытия: скрипт в `scripts/` + отчёт,
  предсказывающий проверяемое состояние.

### S5. Дизассемблирование `AmdNbioGfxARIPei` до истинных регистров (P1.5b) — ЧАСТИЧНО

- В чём пробел: сделано сравнение входов C0A/BC250
  (380 инструкций, 43 прямых вызова, скелеты совпали;
  расхождение только в `0x11BD↔0x13B1`), но сериализация
  Init Config Struct `0x1e0/0x1e1` в NBIO-пространство
  не прослежена — истинные NBIF-регистры не выведены.
- Свидетельство: `memory/firmware-audit.md`
  (разделы 2026-09-14: PEIM entry, gate-value comparison);
  unlock-paths-map п. 2.
- План закрытия:
  1. Продолжить трассировку хелперов и `AmdNbioBaseARIPei`.
  2. Вывести формулу `0x1e0/0x1e1 → NBIO-адрес`.
  3. Только затем — одна обратимая рантайм-битовая запись
     (новый ранбук + аппрув).
- Критерий закрытия: именованный список истинных
  NBIF-регистров с механизмом записи.

### S6. Staged kernel 0012 (путь P4) — ОТКРЫТ

- Свидетельство: unlock-paths-map P4; `memory/project-state.md`

- План закрытия:
  1. Выделить стадии из master plan в отдельный спек.
  2. Собрать 0012 поверх `7.2.0-1.92-cachyos-vcn-bc250`
     параллельно RE-работам (зависимостей от моста нет).
  3. Прогнать на mode1 (нерегрессия probe).
- Критерий закрытия: собранное ядро + успешная mode1-загрузка.

### S7. QEMU-модель SMU/SMN-почтовых ящиков — ОТКРЫТ

- В чём пробел: журналы D5 прямо фиксируют — QEMU не может
  смоделировать BC-250 SMU-эксплойт и SMN-ящики;
  DXE-колбэки тестируются только перешивкой.
- Свидетельство: `docs/action-logs/2026-09-12-d5-unlock-lab-bios.md`
  (UNRUN: «QEMU cannot model…»).
- План закрытия:
  1. Минимальный стаб: эмуляция Q2 `0x23` / Q3 `0x2A/0x2C`
     на уровне «alive/значения из захватов» для прогона
     логики DXE (не таймингов).
  2. Интеграция в `uefi-dxe-validation` как опциональный
     предпрогон перед сборкой кандидата.
  3. Честная граница: стаб проверяет логику, НЕ принятие
     декодером и НЕ тайминги железа.
- Критерий закрытия: D9R-логика проходит стаб;
  D7/D8-контролы документированы как вне зоны стаба.

### S8. Таблица POST-кодов платы — ОТКРЫТ

- В чём пробел: даже с пост-картой (S1/H2) коды не к чему
  привязать: таблицы AMI/AGESA для этого BIOS нет в репо.
- Свидетельство: косвенно — error-audit требует канал,
  но словаря кодов нигде нет (проверено поиском).
- План закрытия:
  1. Извлечь строки/таблицы POST-кодов из `AmdStatusCodeDxe`
     и соседних модулей текущего образа.
  2. Сверить с открытой документацией AMI/AGESA;
     расхождения — в Открытые вопросы.
  3. Положить таблицу в `docs/reference/`.
- Критерий закрытия: файл таблицы + привязка ≥1 кода
  к наблюдению с пост-карты.

### S9. Двухлинзовая RE-дисциплина (Cutter+Ghidra) — ЧАСТИЧНО

  1. Ранбук «поднять Ghidra-MCP → перепись N функций →

### K1. Нет скилла раннего наблюдения (UART/POST/JTAG-read) — ОТКРЫТ

- В чём пробел: ни один скилл не покрывает снятие UART,

  но как процедура не оформлен).
- План закрытия: новый скилл `board-early-observe`:

- Критерий закрытия: SKILL.md + применение на одном

### K2. Нет скилла UEFI-Shell зондирования — ОТКРЫТ

- В чём пробел: `uefi-dxe-validation` покрывает сборку/
  валидацию DXE и Shell-проверки, но не процедуру
  живого DF/SMN-зонда из Shell (инкрементальный порядок,
  лог-каждого-шага, холодный цикл как штатный исход).
- План закрытия: расширить `uefi-dxe-validation`
  разделом `shell-live-probe` ИЛИ выделить
  `uefi-shell-probing` (предпочтительно расширение —
  избежать дробления). Вшить G7-оговорку S3.
- Критерий закрытия: раздел + чеклист + применение на S3.

### K3. Нет скилла staged-kernel сборки — ОТКРЫТ

- В чём пробел: сборка/верификация кастомных ядер
  (1.92 + патчи 0011/0012, mode0/1/2, limine-записи,
  бэкапы `.bak-*`, diff-контроль одной строки) —
  процедура есть в журналах, но не оформлена скиллом;
  ошибка D17 (не то ядро) — прямое следствие.
- План закрытия: новый скилл `bc250-kernel-stage`:
  сборка, установка рядом (не вместо), записи limine,
  предзагрузочный чеклист (ядро+cmdline на экране),
  постзагрузочная сверка (`uname`, `/proc/cmdline`).
- Критерий закрытия: SKILL.md + ретроспектива:
  показать, на каком шаге чеклиста был бы пойман
  конфуз D17.

### K4. Нет скилла программатора/флеш-дисциплины — ОТКРЫТ

- В чём пробел: флеш-дисциплина (захват→сверка→апрув→
  запись→VERIFIED→readback→парсеры→NVRAM-diff→fresh-rebase)
  разбросана по 20 журналам; единого исполняемого чеклиста
  как скилла нет. `artifact-verification` покрывает
  верификацию артефакта, но не операционную процедуру.
- План закрытия: новый скилл `spi-flash-discipline`:
  пошаговый ранбук с командами flashrom/ch347_spi,
  формами апрува, классификатором дрейфа NVRAM
  (адреса/пороги из кейсов 5–6), процедурой STOP.
- Критерий закрытия: SKILL.md, покрывающий D8–D10R
  как эталонный прогон.

### K5. `vcn-smu-probing` не знает таксономии клинов — ЧАСТИЧНО

- В чём пробел: скилл существует, но wedge-taxonomy S2-A
  (безопасные: одиночные чтения, записи gasket;
  смертельные: полные дампы, DF-чтения, DF/SMN из Linux)
  и оракулы (`alive`, `0x2A→0x5A870=0x77`, hw_init `-62`)
  в него не внесены (проверено чтением описаний;
  полное содержимое — см. Открытые вопросы).
- План закрытия: раздел `wedge-taxonomy` + таблица
  «транспорт → класс» + обязательные стоп-условия
  (`alive=False` → холодный цикл, без дальнейших ящиков).
- Критерий закрытия: раздел + ссылка из каждого нового
  рантайм-ранбука.

### K6. `spec-planning` vs «ранг без оснований» (F3) — ЧАСТИЧНО

- В чём пробел: процессный провал F3 (ранжирование баз

- Критерий закрытия: гейт в тексте скилла + применение
  на ближайшем выборе базы/инструмента.

## Часть 3. Железо для отладки

### H1. J5 UART — ОТКРЫТ (разъём известен, подключения нет)

- В чём пробел: аудит называет J5=UART первым каналом,
  но в репо нет ни распиновки J5, ни захвата, ни фото.
- Свидетельство: error-audit строка ~126, forward tree.
- План закрытия:
  1. Найти J5 на плате/бордвью, вызвонить GND/TX/RX,
     проверить уровень 3.3 В TTL (НЕ 5 В, НЕ RS-232).
  2. Подключить USB-UART (3.3 В), снять лог стоковой
     загрузки → сохранить как эталон тишины/нормы.
  3. Задокументировать распиновку + фото + параметры
     порта в `evidence/boardview/` и сослаться из S1.
- Критерий закрытия: эталонный лог + схема подключения.

### H2. TPMS1 POST / LPC пост-карта — ОТКРЫТ

- В чём пробел: второй названный канал (LPC/POST-декод)
  тоже без распиновки, захвата и словаря кодов.
- Свидетельство: error-audit, строки ~224–225.
- План закрытия:
  1. Вызвонить TPMS1 (LPC CLK/FRAME/LAD0–3, GND);
     либо задействовать готовую LPC пост-карту,
     если на плате есть совместимый разъём.
  2. Снять эталонную POST-последовательность стоковой
     загрузки (видео + лог кодов).
  3. Привязать коды к таблице S8; расхождения —
     в Открытые вопросы.
- Критерий закрытия: эталонная POST-последовательность
  + схема подключения.

### H3. J2 CPU JTAG: распиновка есть, процедуры и адаптера нет — ЧАСТИЧНО

- В чём пробел: из бордвью извлечены J2 (`CON_2X10_SAMTEC_FTSH`):
  `CPU_TCK` пин 2, `CPU_TMS` пин 4, `CPU_TDO` пин 8,
  TDI через `J2.6 → N22562912 → R19 → CPU_TDI`,
  TRST# через `J2.9 → N22563682 → R120 → CPU_TRST#`,
  пины 1/19 `+1.8V`, 3/5/7/17 GND. Но: это НЕ физическая
  верификация; JTAG-адаптер под 1.8 В и OpenOCD-конфиг
  под этот SoC в репо отсутствуют; ни одного
  read-only подключения не было.
- Свидетельство: `memory/decisions.md` D10; D8 (JTAG
  read-only по умолчанию).
- План закрытия:
  1. Физически верифицировать маркировку/напряжение J2
     (D9: бордвью — наводка, не идентичность).
  2. Обзавестись JTAG-адаптером с 1.8 В (проверить,
     умеет ли CH347 JTAG — исходим из «нет», нужен
     отдельный: FTDI/J-Link-совместимый).
  3. Read-only триал: IDCODE-скан, без записи в память
     цели (D8). Только после — думать о большем.
- Критерий закрытия: захваченный IDCODE + конфиг
  в `tools/jtag/` + запись в скилл K1.

### H4. Программаторный стек: есть, но single-point — ЧАСТИЧНО

- В чём пробел: рабочий стек (CH347T + flashrom
  `ch347_spi` + SOIC8-клипса + Winbond W25Q128.V)
  доказан ~23 циклами, но: один программатор,
  один чип-прицел, клипса как единственный контакт
  (риск срыва/плохого контакта при каждой итерации).
- Свидетельство: `memory/decisions.md` D11–D12, D14–D15;
  журналы D5–D20 (каждый — цикл клипсы).
- План закрытия:
  1. Запасной программатор (второй CH347 или Bus Pirate —
     зафиксировать модель после `external-stack-evaluation`).
  2. Рассмотреть SOIC8-сокет/переходник под пайку
     для кампаний с десятками циклов (клипса — для
     единичных операций).
  3. Держать две независимые копии цепочки восстановления
     (сток `83c4e420`, pre-m0 `3f836668`) вне рабочей машины.
- Критерий закрытия: второй программатор + успешный
  read-only цикл на нём.

### H5. Логический анализатор / осциллограф для SPI и UART — ОТКРЫТ

- В чём пробел: споры «что именно ушло в чип/эфир»
  (тайминги ch347_spi 15 МГц, кадры UART, LPC-циклы)
  разрешаются только косвенно (VERIFIED/readback).
  Прямого захвата сигналов нет.
- Свидетельство: косвенно — все SPI-циклы D5–D20
  (ни одного сигнального захвата в evidence).
- План закрытия:
  1. Дешёвый захват: Saleae-совместимый клон 24 МГц
     для UART/LPC-декода (процедура через скилл K1).
  2. Для SPI 15 МГц — анализатор ≥100 МГц либо
     осциллограф; только если появятся необъяснимые
     VERIFIED-фейлы.
  3. Хранить захваты в `evidence/signals/` с хешами.
- Критерий закрытия: один эталонный захват UART-лога
  стоковой загрузки (дублирует H1 независимым путём).

## Упражнения

### Упражнение 10.1. Триаж тишины

Плата после прошивки молчит: LED статичен, сети нет.
По карте этой главы: какие три канала наблюдения
применяете и в каком порядке? Что должен показать
каждый, чтобы различить «PSP отверг» vs «ABL упал»
vs «DXE висит»? Какой пункт карты при отсутствии
всех трёх каналов запрещает делать вердикт?

Ответ: порядок — (1) J5 UART-лог (S1/H1): наличие
ранних строк AGESA/ABL vs полная тишина с первой
миллисекунды; (2) POST-коды TPMS1 (S1/H2+S8): код
останова привязывается к фазе по таблице;
(3) read-only JTAG IDCODE/останов-статус (H3/K1):
жив ли TAP-контроллер и где остановлен CPU.
«PSP отверг» — тишина UART с нуля + ранний POST;
«ABL упал» — обрыв UART на фазе ABL + код ABL;
«DXE висит» — поздние коды + UART до DXE-диспетча.
Вердикт без каналов запрещает standing rule
instrument-first + anti-G6 (S1, K6): молчание без
канала — ненаблюдение, а не результат.

### Упражнение 10.2. Ретроспектива D17

Примените чеклист несуществующего скилла K3
к конфузу D17 (оператор загрузил стоковое ядро 1.1
вместо mode1 1.92). На каком шаге чеклист ловит ошибку?
Сколько лишних прошивок это сэкономило бы, если бы
скилл существовал до D17? Обоснуйте число.

Ответ: ошибка ловится на предзагрузочном шаге
«ядро+cmdline на экране» (сверить выбранную запись
limine до нажатия Enter) и дублирующе — на
постзагрузочной сверке (`uname -r` + `/proc/cmdline`
до запуска SMU-проверок). Сэкономленных прошивок — 0:
вердикт D17 по SMU-слою устоял (клин доказан независимо
от ядра), пострадала только чистота режима (режимный
конфуз, не ложный вердикт). Ценность K3 здесь —
не сэкономленные циклы, а неснижение класса
свидетельства будущих рунгов.

### Упражнение 10.3. Приоритизация при одном вечере

Доступен один вечер operator-time. Кандидаты: (а) снять
J5-UART эталон (H1); (б) собрать Shell-хелловорлд (S2);
(в) начать P1.5a-RE (S4). Расположите по приоритету
с опорой на зависимости карты и правило anti-G6.

Ответ: (а) → (б) → (в). H1 — разблокирует класс:
без канала запрещены все будущие вердикты о молчании
(anti-G6/S1), а эталон нужен до первой аномалии.
S2 — разблокирует S3 (Shell-зонд), который есть
единственный разрешённый живой путь к DF/SMN (D17).
S4 важен (первичный путь P1.5a), но чисто офлайнов:
его можно делать без оператора и платы в любое время,
поэтому при дефиците operator-time он последний.
Общий принцип карты: сначала каналы наблюдения,
затем живые контексты, затем офлайн-анализ.

## Открытые вопросы главы

1. Распиновки J5 и TPMS1 в репо нет — только названия
   из аудита; физическая верификация не проводилась.
2. Полное содержимое скиллов (кроме description) для
   K5 проверено не побайтово: утверждение «таксономии
   клинов в скилле нет» опирается на описания и поиск;
   при расхождении — скорректировать K5.
3. Совместимость CH347 с JTAG-функцией не проверялась;
   H3 исходит из «нужен отдельный адаптер» как из
   рабочей гипотезы.
4. Таблица POST-кодов S8: неизвестно, существуют ли
   коды в открытом виде в `AmdStatusCodeDxe` этого
   образа — извлечение не пробовалось.
5. QEMU-стаб S7: неизвестен объём работ (дни vs недели);
   оценка — после первого прототипа Q2/Q3-стаба.
6. H1–H5 ничего не говорят о стоимости/сроках закупки —
   в репо нет данных; при появлении — дополнить.
