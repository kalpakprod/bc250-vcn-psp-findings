# CLV ABL1: найдены выходные запросы настройки FCLK и UCLK

## Существенный результат

В функции ABL1 `0x5E68` обнаружена не только запись вычисленного слова в структуру. Дальше выполняются два SVC#0x28 запроса, возле которых сам BIOS печатает `PSPSMC_MSG_SetupFclkPll` и `PSPSMC_MSG_SetupUclkPll`.

Точный ABL1 SHA256 af8cf5626a113afe72bc0687ca6f1a3b44fd6d46ca4f0119df3be2356a74203a. Связь с clean CLV сохранена в существующих provenance-артефактах. Проверка не меняет прошивку и не вызывает эти сервисы на плате.

## UCLK: явное деление входа на два

- Caller `0x7E40` загружает значение context+0x2BC, затем `0x7E6E` передаёт его в R2 функции5E68.
- `0x5E74`: R4=входной R2.
- `0x5F30`: `LSR.W R8,R4,#1`.
- `0x5FF4..0x5FFA`: R0=0x0F, R1=R8, R2=SP+8, SVC#0x28.
- ADR при0x5FEC указывает на точную строку `Send PSPSMC_MSG_SetupUclkPll  0x%x`.

Следовательно, на этой ветке аргумент UCLK-сервиса формируется как половина входного32-bit слова с округлением вниз. Это конкретный код делителя, а не трактовка названия UclkDiv1M0. В начале R8 получает входной R1, но инструкция5F30 ПЕРЕЗАПИСЫВАЕТ его. Нельзя приписывать позднему SVC исходный R1.

Это ещё не доказательство физических MCLK:UCLK=2:1: нужны единицы и семантика сервиса, а также реальная достижимость ветки. Пока корректно говорить о делении численного аргумента. Для арифметического примера вход1800 даёт900, не о замере платы.

## FCLK: явный приоритет значений перед отправкой

До0x5F9A есть расчёт на основе входной частоты. Однако последующий безусловно проходимый блок заменяет локальное слово:

- nested `[context+4]+0x790` равно6 → слово250 через0x6028;
- иначе → слово1200 через0x5FA4;
- затем0x5FAE вызывает463C с указателем на слово и selector0x0F;
- если provider1FB4 внутри463C возвращает ненулевой результат, считанный u16 заменяет слово. Иначе локальный default сохраняется;
- после возврата слово пишется в context+0x78 и передаётся SVC28 с R0=0x0E, R1=слово, R2=SP+8.

Вызов463C строит descriptor015F/0160. Его конечный источник и связь с AmdSetup DfClockOvrd ещё не доказаны. Не называть descriptor CBS-токеном по сходству чисел.

## Почему это меняет следующую работу

Ранее обсуждались в основном агрегирование данных95FC и внешний callback. Теперь есть конкретная выходная граница PLL-сервисов и прямой арифметический кандидат, который может объяснять половинный режим. Следующий опыт должен исполнять этот участок с перехватом SVC и проверять реальный приоритет default/provider, затем установить семантику SVC28. Не патчить LSR вслепую: удвоение аргумента сервиса без проверки единиц способно выбрать неподдерживаемую частоту.

## Важные ограничения

Это static byte-backed результат, не эмуляция. Python unicorn не установлен в проверенных интерпретаторах, установка не выполнялась. Полный путь не исполнялся. Служебные logging/provider вызовы и ABI сохранения R4/R8 не проверены исполнением. SVC handler и перевод локальных selectors0E/0F в аппаратные сообщения не исследованы здесь. Не путать их с одноимёнными номерами Linux/SMU mailbox другого интерфейса.

Существующий95FC gate уже исследовался раньше. Строка называет его Multi-Die DRAM Speed Sync: это не само по себе синхронизация MCLK/UCLK/FCLK. Его повторный разбор не выдан за новую находку.

## Native runtime-HEAP → PLL, следующий проход

Удалена подмена lookup4800. Первый ограниченный прогон оригинального4800→49CC→6374 остановился при чтении адреса73000: UC_ERR_READ_UNMAPPED на637C. Это отсутствующая модель runtime heap, не ошибка BIOS и не доказательство отсутствия настройки. Ошибка и последние PC сохранены в provider-probe-result.json.

Затем отдельно задан ЯВНО синтетический HEAP-cache: magicHEAP, node keyA04E, таблица с pointer на data, строки token015F/0160 с шестибайтным шагом и типами1/2. Для встроенных абсолютных указателей данных добавлен отдельный образ по условной базе57100. Эта база и cache не выдаются за снятое состояние реального boot.

Новый стенд `emulate_pll_heap.py` исполняет оригинальные4800,49CC,6374,1FB4,463C и PLL-builder. Подменяются только logging130C и конечные SVC-ответы. Кэш-hit путь доказан в данной среде, его первоначальное заполнение не исполняется и остаётся неизвестным. Все9 прежних различающих случаев сохраняют ожидаемые выходы, в том числе блокировку gate0/missing иFFFF. На пути успешного1420 override исполнено569 инструкций вместо242 при подменённом lookup.

Конкретный формат применённой runtime-записи:

- lookup group15 выбирает keyA04E;
- pointer table base+8+6*(token-1) даёт descriptor;
- флаг присутствия для первой таблицы находится в младшем бите;
- ширина=(flags bits2..4)+1;
- source selector byte1 допускает текущий selector15 или общий1;
- u16 descriptor+2 задаёт offset в data по pointer table[0].

Это формат runtime-cache в этой функции. Не отождествлять его с APCB на SPI или CBS INV record layout. Ни один cache token не приписывается полю AmdSetup без связи producer→cache.

Команда: `tools/abl-emulator-venv/bin/python evidence/firmware-audit/20260923-abl95fc-next/emulate_pll_heap.py`.
Результат: PASS9 native HEAP-to-PLL cases, unchanged code, only declared external-effect hooks.
Результаты: emulation-heap-result.json, heap-verification.json. ROM и исполняемый образ ABL1 по адресу0 не менялись. Отдельная data-alias область является частью тестовой среды.

Следующая незакрытая задача: заполнение A04E не через искусственный cache и обработчик SVC28. Новое исполнение подтверждает путь из cache к запросу, а не аппаратный эффект или доступность этих значений из BIOS-меню.

## Существенное продолжение: источник взят из настоящего APCB чистого ROM

Cold-cache проход показал: функция4E4C читает конфигурационные группы по фиксированному указателю7B000, literal4F2C. Это отдельный вход среды, не часть ABL1. В первой модели диапазон случайно попадал в нулевую RAM-зону и возвращал отсутствие записи. Этот результат сохранён как cold-empty-source-result.json и НЕ принимается за поведение stock BIOS.

В исправленную модель по7B000 помещены реальные2972 байта APCB из clean CLV ROM0xAB1000. Пустой HEAP создаёт оригинальная функция63F8, а не вручную заданный header. Оригинальный49CC сам создаёт A04E, вызывает4E4C и заполняет cache. Подмена token lookup отсутствует.

Получен byte-backed + executed источник:

- Group1707/type000F, gate token015F: исходный байт APCB+0xB99 (ROM0xAB1B99) равен1.
- Value token0160: исходное u16 APCB+0xB9A (ROM0xAB1B9A) равно1420.
- В trace: база данных7B864, смещения821/822, что даёт7BB99/7BB9A соответственно.

Пять сквозных опытов emulate_pll_apcb.py:

| --------------------------------------- | --------------------: | --------------------: |
| Чистый APCB, memory word1800            |                  1420 |                   900 |
| Только APCB FCLK word1430 плюс checksum |                  1430 |                   900 |
| Возвращён чистый APCB                   |                  1420 |                   900 |
| Gate015F=0, value1430 плюс checksum     |                  1200 |                   900 |

Все5 проходят, код неизменён. Изменения только в копии APCB внутри памяти эмулятора. Checksum APCB пересчитан по существующей sum8-схеме offset10, исходный/изменённый варианты имеют sum modulo256=0. Нового ROM не создано.

Это впервые в данном execution-loop соединяет реальные байты конфигурации выбранного clean ROM с аргументом PLL-запроса без синтетической подмены cache/lookup. Однако копирование именно этого APCB в runtime7B000 остаётся предпосылкой модели: предшествующие загрузчик, выбор APCB и возможные наложения NVRAM ещё не исполнены. Поэтому совпадение1420 в AmdSetup и APCB не доказывает связь этих двух хранилищ. Исторические профили, меняющие только первые0x20000 ROM, не меняют этот APCB-источник, но могут влиять через пока неустановленное runtime overlay.

Первый20k instruction limit был исчерпан во время построения таблицы. Лимит увеличен до150k и2s без снятия проверок, выполнение закончено примерно44.9k инструкций. Лог исходной остановки сохранён в cold-apcb-20k-limit.json. Отдельно первый ручной heap-header и необработанный event logger привели к ограничению бюджета, не к доказанному firmware hang. Итоговый стенд выполняет native initializer и явно перехватывает event logger112A0.

Следующий шаг: установить loader/overlay источник runtime7B000 и семантику SVC28. Практический патч можно обосновывать на найденном APCB-слове, но до этих проверок и решения SoC это не готовый разгонный BIOS.

## ABL0 подтверждает назначение runtime7B000

Из точного clean CLV извлечён ABL0 (SHA2563405551617c13dc7b1db464edd74e0f7a4240a80b37ed068c7650ccfe2d19e29). Поиск literal7B000 дал реальные ранние ссылки0x70/0x118. Функция30 исполняет SVC#2D с R0=60,R1=7B000,R2=указатель на размер, начальная ёмкость2000. Затем вызывает native validatorB8, который проверяет APCB magic, версии/размер/непустой идентификатор и sum8. Это не случайно выбранный тестовый адрес: его запрашивает загрузочный код.

В clean BHD при ROM0xAB0010 находится type60,size2000,sourceFFAB1000,destinationFFFFFFFFFFFFFFFF. Source физического SPI-окна соответствует ROMoffsetAB1000. Это статический directory candidate, который согласуется с APCB, использованным в эмуляции. SVC2D handler пока не исполнен: выбор именно этой записи и отсутствие дополнительных преобразований не доказаны.

Исполнены4 ABL0 случая в emulate_abl0_load.py:

- BASELINE: SVC2D fixture передаёт настоящий clean APCB, native validation проходит, функция возвращает0.
- Bad checksum: изменён один байт без пересчёта, native validator отклоняет, достигнут SVC0 с fatal code16.
- Service failure: SVC2D fixture возвращает ошибку, достигнут тот же fatal path.
- RESTORED: исходный APCB снова принят, hash загруженных байтов совпадает.

Logging SVC6 явно моделируется без изменения регистров. Остальные неизвестные SVC приводят к ошибке, не заменяются успехом. Код ABL0 неизменён. Source/result evidence: ABL0.bin, abl0-apcb-validation.txt, abl0-load-result.json. Передача через service fixture не выдаётся за реальную работу ROM-handler.

Ограничение, важное для1:1:1: текущий PLL path относится к ранней инициализации (`GnbSmuInitAblCAR`), не доказывает установившийся режим после обучения и последующих переключений DF P-state. Нельзя называть LSR1 доказанной причиной конечной задержки или удалять его, не проверив последующие переходы.

## Более позднее переключение в ABL4 и кандидат SMU-handler

В exact ABL4 найден отдельный вызов: D8AE задаёт аргумент100, D8B2 вызывает9564. Original9564 вызывает неизменённые topology helpersA418/A450, затем SVC28 selector7,argument100. Собственная строка кода: SwitchToStartupDfPstate. Native ARM emulator проверил stock caller и wrapper inputs101/100, три случая прошли с перехваченным аппаратным сервисом. Arg100 не обозначает100MHz: его кодировка отдельна.

Fresh read-only Ghidra разбор exact SMU robin5 выявил согласованную кандидатную семью dispatch:

- entry79E8,ID7 →1E720;
- entry7A20,ID0E →1F218;
- entry7A28,ID0F →1F2F0.

Это семейство в retained inventory называется Queue4. Другие отчёты нумеровали такие таблицы иначе, поэтому авторитетны адреса, не человеческое имя очереди. Прямое соединение SVC28 с этой очередью ещё не доказано. В queue0 те же ID имеют совсем другие функции, их подстановка была бы ошибкой.

Обработчик1E720 разбирает старший байт и младший индекс. Для100 старший байт1 выбирает явный state index0, проверяет его против количества состояний, ставит state+F6=FF и вызывает1E448. Это согласуется с запросом startup state, но не доказывает транспортную связь.

Обработчики1F218/1F2F0 отказываются при state+F6=FF. Оба отвергают нулевой аргумент, переводят целое в float и умножают на0.001. Первый вызывает clock-domain helpers для domain0E, второй для0F/11 и вспомогательных10/12. Величины и назначение доменов нельзя считать независимым измерением MHz. В отличие от decompiler-псевдокода, реальные инструкции и каждый literal сверены с байтами exact SMU и исходным ROM-slice.

Последствие: ранние PLL-запросы могут относиться к режиму инициализации до перехода на таблицу DF. Патчить начальное деление пополам и обещать конечное1:1:1 преждевременно. Нужно связать конкретный сервис с очередью и проверить происхождение/обновление выбранной строки. Статические числа из образа SMU не объявляются неизменяемыми пределами железа.

Artifacts: startup-df-result.json, smu-pll-handlers.txt, smu-transition-helpers.txt, smu-transition-result.json. Код прошивки не менялся. Headless Ghidra -readOnly -noanalysis, max1CPU, изменения project discarded. Все выводы про SMU static, не native SMU execution.

## Очередь: устранена неоднозначность нумерации

В raw SMU вектор указателей7A94 содержит8 элементов. Индексы3 и4 оба указывают на746C. Семейство PLL по79B4 находится в элементе5, а не4. Название Queue4 в старом перечне считало уникальные таблицы, пропуская повторную ссылку. Не использовать это название как номер аппаратного канала.

Свежий read-only decompile00FFC/00FA8 и16 byte-checked инструкций подтверждают:

- accessor аргумента читает через pointer по base7000+0xC+index*12;
- accessor ответа пишет через pointer по base7000+0x10+index*12;
- для index5 это внутренние адреса03010700/03010704;
- соседнее поле descriptor03010718 обозначалось command в retained layout, но сам dispatcher здесь не исполнялся.

Для index5 IDs7/0E/0F указывают на1E720/1F218/1F2F0. Для index4 это другое семейство: ID7 отсутствует, ID0F ведёт на27E94. Поэтому использование человеческого Queue4 как индекса вызвало бы обращение не к тем обработчикам. Ни одного такого обращения на плате не выполнялось.

Проверка не соединяет SVC28 с каналом5 автоматически. Она уточняет конкретный адресный контракт для следующей проверки transport. Также не выдаётся команда доступа к внутренним SMN-регистрам из ОС.

Артефакты: smu-mailbox-accessors.txt, queue-binding-result.json. verify_queue_binding.py проверяет полную идентичность sourcehash,16 инструкций и8 descriptor/vector entries; чтения msg за границей коротких таблиц не интерпретируются как handlers.

## Проверка доступного PSP-диспетчера: не тот сервисный контекст

В PSP directory8E0000 обнаружены type1 по8E0400 и type2 по8EBA00. Первоначальный краткий inventory ошибочно проверял $PS1 поoffset0. Исправлено по существующему parser: magic находится поheader+10. Первая версия сохранена, отсутствие magic type1 не трактуется как доказанное шифрование.

Type2 имеет encrypted0,compressed0, plaintext body78160 bytes, SHA256259a31d52ec847df23596ae1c7e736212ff6bab7793af741b83fa62e439ade68. Это retained PSP_FW_TRUSTED_OS. Код содержит ARM exception vector+8→240, разбор Thumb/ARM SVC immediate и BLX через4545→Thumb4544.

На обычном dispatcher route4544→46A0 service index уменьшается на51 и проверяется против80. Поэтому ранние ABL selectors28 и2D уходят в default-return9, а не к SMU или loader. Это подтверждено двумя исполнениями native46A0 в отдельном Unicorn instance с синтетическим saved-register frame. Никакие MMIO/hardware callbacks не подменялись, исходный code region0..6000 неизменён. Exception prologue и выбор task-class не исполнялись.

Практический вывод: наличие plaintext TrustedOS ещё не даёт обработчик раннего ABL SVC28. Нельзя склеивать два разных этапа PSP только по одинаковому номеру SVC. Transport edge до SMU не закрыт. Для этой ветки нужен соответствующий ранний bootloader/ROM service implementation либо трасса, а не дальнейший перебор TOS syscall-таблицы.

Artifacts: psp-transport-inventory.json, psp-type2.bin, tos-boundary-result.json, verify_tos_boundary.py. Нового ROM не создавалось. Type1 остаётся неклассифицированным payload, не объявлен зашифрованным по одной энтропии/неизвестному header.

## Граница раннего сервиса и независимая проверка DF query

Type1 PSP payload по8E0400 имеет hash0bfbd84a89fc07ecd6fbfadde9e49f0af58aa42a87212b84e252313716efd851,size46592. Существующий parser выбранного ROM также сообщает not-a-$PS1-container. Открытого совпадающего plaintext handler в проверенном наборе нет. Энтропия не использована как доказательство шифрования. Ветка поиска раннегоSVC handler остановлена на отсутствующей реализации, не на доказанной невозможности управления частотами.

Независимое полезное уточнение: ABL QueryMemFreqOfDfPstate посылает selectorA. В кандидатной SMU таблицеindex5 IDA→1E7D8. Обработчик проверяет runtime count, загружает rowpointer изCEE0+1C+4*index и возвращает float поrow+18, преобразованный в unsigned integer. Аппаратного чтения PLL в этом query нет. Поэтому такой ответ сам по себе не является независимым измерением частоты.

В начальном образе SMU row+18 равны450,450,850,1750,250 для строкCF0C/CF34/CF5C/CF84/CFAC. Эти значения не являются ни подтверждёнными конечными частотами, ни пределом разгона. Runtime writer может изменить строки.

Дополнительный handler1E650 (ID D) действительно выбирает состояние через1E448, а не возвращает количество состояний. Файл исследования сохранён с первоначальным именем smu-df-count.txt, но смысл исправлен по прочитанному коду. Сам ABL-запрос количества использует selector8, неD. Это ещё один повод связывать по точным callsites, а не угадывать номера.

verify_df_rows.py проверяет55 инструкций нужных entry и5 исходных row values. Предположительно начатая с1E994 функция исключена из выводов: адрес не подтверждён как entry dispatch table. Артефакт сохраняет эту исследовательскую попытку, но она не является результатом.

Следующий конкретный вопрос: кто пишет row+18 после загрузки SMU, и какие данные использует1E038 при выборе rowpointer. Ранее проверенную статическую таблицу не проверять ещё раз ради PASS. SVC transport остаётся открытым и не препятствует независимой проверке писателя.

## Писатель строки DF: результат ограниченного поиска

Проверены конкретные кандидаты по ссылкам на структуруCEE0. Функция21E8C пишет float-массивF104, не выбранную строкуDF.1E038 строит rowpointer/index metadata.1F098 читает поля выбранной строки.1F3F4/1F52C обслуживают счётчики/накопители.1F120 переносит содержимое регистра53A60 между каналами и хранит последнее значение поCF78+8*i+80;1F198 запускает/ожидает handshake53A58/53A5C. Они не доказаны как писатели искомогоrow+18.22D6C содержит ещё не закрытые транзитивные вызовы, исключать их нельзя.

Первый поиск по уже определённым инструкциям Ghidra дал неполное покрытие, поскольку prior read-only passes не сохраняли созданные функции. Его малое число совпадений НЕ означает отсутствие писателей. Затем использованы raw l32r leads и целевые decompile с полной сверкой инструкций по исходным байтам. Отрицательный результат остаётся ограниченным показанными функциями.

Результат задачи здесь: runtime writer не установлен. Нового регулируемого параметра или патча это исследование не обосновало. Не представлять очередную зелёную проверку как получение разгонного профиля. Следующий полезный путь должен закрывать конкретную транзитивную связь22D6C, а не повторять53-кандидатный список.

Артефакты: row-writers.txt, df-row-candidate-setters.txt, df-domain-queries.txt, row-writer-result.json. Все обращения были offline/read-only. Java scanner не изменял проект, но его coverage недостаточно для отрицательного вывода.
