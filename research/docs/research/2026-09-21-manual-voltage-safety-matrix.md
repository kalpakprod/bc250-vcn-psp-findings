# Manual VCORE/GFX/MEMIO voltage-entry safety matrix (CLV 5.00)

Date: 2026-09-21 (Asia/Almaty)  
Current: exact CLV Setup fields and static consumer paths summarized / memory request 1800 retained / physical rails and safe values unknown / no setting recommended.

## Conclusion

**No numerical manual VCORE, GFX, or MEMIO value can be recommended from the available evidence.** The exact BIOS exposes syntactic field ranges/options and static PEI code that consumes the named fields, but neither the firmware path nor the available board references establish the physical rail/page mapping, the controller's voltage encoding, the applied output, or a safe electrical range for the operator's board revision. An IFR bound or option label is not a voltage safety limit.

Keep the memory request unchanged at the pinned donor's `AmdSetup+0x316 = 0x24` (`1800MHz` IFR label). This is a stored request, not a confirmed physical clock or a voltage requirement. Do **not** assume that any VCORE/GFX/MEMIO field sets SoC voltage or that `1.15 V` can be represented by one of them.

## Classification key

- **Observed field range/options**: static IFR/HII bound or enumerated label in the exact donor. It describes what the field advertises, not what a physical controller accepts or what is electrically safe.
- **Observed static code path**: disassembly shows which field/default bytes are selected and staged. It does not prove PEIM dispatch, bus transfer, PMBus semantics, rail identity, or applied voltage.
- **Unknown / unsupported for recommendation**: missing identity, conversion, readback, or board-specific electrical limit. Do not fill these gaps by mapping labels or values across rails.

## Firmware and applicability limits

The payload trace is static evidence over the pinned CLV bytes. `ISL69247` uses fixed page-selector payloads `0` and `1` in its VCORE/GFX-named code blocks; the independent payload report specifically warns that labels `0x00`/`0x21` and the transmitted values do not, by themselves, establish PMBus PAGE/VOUT semantics. `ISL95712` consumes the MEMIO-named fields and stages target index `0xDF`, but the register semantics remain unknown. In both decoded entry paths the disabled branch still stages a default/control write; `Disabled` must not be interpreted as “the firmware makes no voltage-related writes.”

Both PEIMs have a static depex requiring two PPIs; the producer of the second PPI is unresolved and runtime dispatch is unproven. The checked entry paths show no board/SKU or VR-ID test before mailbox activity. Firmware presence and module names therefore do not certify that the code targets the live board's rails. The community board annotation identifies PUA1 as an ISL69247 “Main PMIC” and PUIO1 as an ISL95712 “Core supply PMIC,” but is not a revision-matched netlist and does not map page/output to CPU, SoC, GFX, or MEMIO. No page-to-rail recommendation follows.

## AMD guidance boundary

The checked Ryzen Master guide text extraction co-lists `VDDCR SOC` and `CLDP VDDG` with a typical `1.1 V` starting phrase in a DDR4 / Ryzen 3000 memory-overclocking context. The raw AMD PDF was not retrieved; the exact printed spelling/wording and the electrical relationship between VDDG and SoC remain inconclusive. Even if taken as extracted, this is not a maximum, not `1.15 V`, not a BC-250/Cezanne GDDR6 limit, and not a manual VCORE/GFX/MEMIO recommendation. The guide’s p. 20 “maximum allowable” wording concerns CPU-core voltage under the present control mode, not a universal SoC/GFX electrical ceiling. Do not silently change `CLDP` to `CLDO` or treat it as a synonym. Community CPU-core VID examples/cautions are likewise not SoC or GFX advice.

## Decision

**Manual fixed-voltage profile: NO-GO on current evidence; no numeric value is endorsed.** This is a limit on what the evidence supports, not a declaration that the donor/default settings have been hardware-validated as safe. The immediate safe evidentiary choice is to make no voltage change and retain the memory request `0x24` without claiming it is physically applied.

A later recommendation would require, at minimum: (1) exact board revision and controller/output-to-net mapping that explicitly joins each named field/page to the physical rail; (2) exact part/mailbox encoding and voltage conversion evidence; (3) revision-matched electrical ratings and limits for the board, regulator, silicon, and memory; (4) evidence that the PEIM dispatches and an independent measured readback of actual voltage. A value fitting the Setup bounds alone meets none of these requirements. Any hardware experiment also remains a separate operator approval/recovery gate.
