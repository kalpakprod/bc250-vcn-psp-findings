## 2. v2000a / vcn_v2_0 power-up chain as the driver performs it

Source: `recon/vcn_v2_0.c` (upstream v6.8 lineage per the project's
2026-09-14 retrieval record in `docs/action-logs/2026-09-14-driver-start-contract.md`
— torvalds/linux tag v6.8 comparison). Sequence of `vcn_v2_0_start`:

1. **SMU power request first**: `if (adev->pm.dpm_enabled) amdgpu_dpm_enable_vcn(adev, true, 0);`
   [static-analysis]. This is the driver's demand that the SMU side raise
   VCN power before any VCN MMIO is touched.
2. `vcn_v2_0_disable_static_power_gating` (non-DPG path): writes
   `mmUVD_PGFSM_CONFIG` with per-block power commands (UVDM/UVDU config=1,
   and either 2 for the rest under `AMD_PG_SUPPORT_VCN` or all-1 without),
   then busy-waits `SOC15_WAIT_ON_RREG(VCN, 0, mmUVD_PGFSM_STATUS,
UVD_PGFSM_STATUS__UVDM_UVDU_PWR_ON_2_0, 0xFFFFF)`; finally clears
   `mmUVD_POWER_STATUS` bits 0x103 [static-analysis, exact lines quoted in
   the action log of 2026-09-14].
3. `UVD_STATUS |= UVD_STATUS__UVD_BUSY`; disable software clock gating
   (`UVD_CGC_CTRL`, `UVD_CGC_GATE`, `UVD_SUVD_CGC_*`) [static-analysis].
4. Enable VCPU clock: `mmUVD_VCPU_CNTL |= UVD_VCPU_CNTL__CLK_EN_MASK`;
   master interrupt disabled during setup [static-analysis].
5. LMI/MPC/MUX setup, `vcn_v2_0_mc_resume` (SRAM scratch in VRAM),
   release VCPU reset (`mmUVD_SOFT_RESET` VCPU_SOFT_RESET=0), un-stall
   `UVD_LMI_CTRL2__STALL_ARB_UMC`, clear `LMI_SOFT_RESET`/`LMI_UMC_SOFT_RESET`
   [static-analysis].
6. Handshake poll: up to 10×100 iterations of 10 ms each polling
   `mmUVD_STATUS & 2`; on timeout, pulse VCPU_SOFT_RESET and retry; then
   "VCN decode not responding, giving up!!!" [static-analysis]. The fw
   boot (ucode from `navi10_vcn.bin`-class binary loaded by
   `amdgpu_ucode`/PSP) must answer here.
7. Master interrupt enable, ring setup (decode RB + 2 encode RBs),
   readback of `mmUVD_STATUS` [static-analysis].

SMU-side complement: `cyan_skillfish_ppt.c` contains **no**
`dpm_set_vcn_enable` callback, and the shared framework
(`smu_dpm_set_power_gate` → `smu_dpm_set_vcn_enable`) returns 0
immediately when the callback is NULL (v6.8 record,
2026-09-14 action log). So on the public Cyan Skillfish driver the
step-1 SMU request is a no-op: reported success without hardware commands
[static-analysis + prior root record].

What the v2000a (Renoir) donor shows: the V2000A PSP dir carries the same
structural families as BC-250 (RenoirRoot.tkn, security_policy_RN_FP6_AM4
PspBl/tOS, prod_kdb) [observed-bytes]. The Renoir BIOS powers VCN through
its PSP/ABL boot policy before the driver ever runs; the driver steps 2-7
then operate on an already-powered, already-clocked tile. That is the
comparison BC-250 fails: on BC-250 the boot-side power release is itself
the blocked stage (§4).

## 3. The 8c-unlock rung (FV-graft framing)

Authoritative secondary source (corpus-local):
`docs/reference/amd-bc250-docs/source/docs/system/8core-unlock.md`,
with provenance credits quoted verbatim there: register documentation and
Linux tool from **GabriWar** (bc250-core-cu-unlock, RE'd from
**Forbidden-Darkness**'s `MeiMeiDXE-T-v2` `Bc250CoreUnlockDxe` driver);
ACPI tables from **mendesrr** (bc250-acpi-fix-updated-8c) rebuilding the
bc250-collective fix. Local provenance of the community commit metadata:
`recon/core_unlock_commits.json` (rw-r-r-0644/bc250-core-unlock HEAD
`fb7e5bce`, 2026-07-31, unsigned) [observed-bytes].

Mechanism (all from the cited doc, static class):

- Register `SMN 0x0115A870` = per-core enable mask. Stock `0x77` (cores
  3 and 7 clear), unlock `0xFF`. Not writable directly; set via SMU
  mailbox **msg `0x98`**: arg0 `0x115A870` at `0x3B10A88`, msg id at
  `0x3B10A20`, poll `0x3B10A80` == 1. Governor must be stopped (0xB8/0xBC
  index/data race hazard).
- Persistence: warm reboot keeps the mask, cold boot reverts to `0x77`
  (nothing written to flash by the Linux method).
- ACPI consequence: 6-core SSDT-CST leaves CPUs 12-15 without C-states;
  the mendesrr 8-core rebuild extends declarations to C00F and installs
  via initrd ACPI override (kernel-side, not flash).

FV-graft surface — what an FV would need to carry:

1. A DXE module performing the msg-0x98 sequence pre-OS on every boot
   (the `Bc250CoreUnlockDxe` pattern): the write itself, i.e. 4 SMN
   writes + poll. No UEFI structural change beyond FFS placement.
2. The ACPI table change (8-core SSDT-CST/SSDT-PST), either as FV-borne
   tables replacing the 6-core SSDTs or left to initrd override. These
   tables live on the **unsigned** APCB-adjacent surface our project has
   already proven boot-safe for APCB-class edits (D3-A/D8-D19 record in
   `specs/2026-09-17-vcn-fclk-mem-campaign.md` §6), though the SSDT
   carrier in this BIOS is UEFI FFS, not APCB — the graft method would be
   the same-slot FFS replacement, not an APCB token edit.
3. Nothing on the PSP-signed side.

Our evidence on whether the BC250 SMU accepts the write:

- The substrate is verified on our board: D9R/D10R boot + unlock PASS,
  and verification literally read mask `0x115A870 = 0x77` (stock 6C)
  [hardware-verified, `docs/research/2026-09-17-thelamer-baseline-delta.md`].
- Q3 arbitrary-SMN-write capability passes as a privileged primitive;
  "arbitrary user reachability and VCN effect are not proven"
  [`docs/research/2026-09-15-independent-unlock-review.md`, verdict table] — i.e. the transport
  class (SMU writes SMN on our behalf) is demonstrated, but the specific
  msg-0x98 write of 0xFF has **never been applied on this board**.
- That boot firmware itself wrote `0x77` into `0x115A870` shows the
  register is SMU-writable at boot time [inference from the readback
  above].
- Known runtime cost documented in the community doc: pp_dpm_sclk
  reporting breaks (monitoring only), ACPI tables must match, existing
  OC/UV curves must be re-validated.

Rung shape: fully reversible (cold cycle restores `0x77`), no flash for
the Linux-method form; the FV form is one flash cycle with a same-slot
FFS graft plus the signed-region rule respected. Per the campaign
standing rule (instrument-first), the runtime form should be preceded by
the boot-observation channel or an explicit waiver.

## 4. Tie-in to the C1 chain state

From `docs/research/2026-09-17-decode-1-6-verdicts.md` (root, 2026-09-17):
the static C1 chain is
`[svc #0x5E/5F handler populates SRAM 0x69D38 table] -> t28 dispatch
0xE6A8 -> fw_type-13 handler 0xE7BC (svc write 0x00185103 -> 0x1F820) ->
release block 0xFCC8 (1->0x0900C004, 1->0x1F8A4, 5 table ops) -> VCN up`,
and **msg 0x8/0x9 (PowerDown/UpVcn) = NULL in BOTH SMU versions**
(community claim confirmed byte-level; 128 implemented / 41 NULL, t3 base
SRAM 0x746C).

Comparison against §2:

1. The v2000a/VCN-2.x driver path **assumes** a SMU-side power-up step
   (`amdgpu_dpm_enable_vcn` → `dpm_set_vcn_enable` → PPSMC PowerUpVcn,
   msg 0x9 in the reference ABI). On BC-250 that message slot is NULL in
   the shipped SMU binary, and on public Cyan Skillfish the callback is
   NULL in the other direction (PPT side) — two different absences that
   agree on one outcome: **no runtime actor issues the SMU-side VCN
   power-up**.
2. Therefore, in the stock layout, VCN power comes only from the PSP-side
   boot release block (t28 chain above). That block exists and dispatches
   fw_type 13, but the hardware rejection observed is `0xFFFF0009`
   occurring **upstream** (descriptor validation / memory reservation
   0x11460), so the release never fires on BC-250 [static-analysis +
   hardware-verified rejection, root verdict 5].
3. This explains, and is consistent with, the runtime layer's behavior:
   first VCN MMIO wedges while the domain is gated; donor gasket/
   aperture/clock work (59/59, slots ON/READY) still leaves the island
   isolated because the dom14-cluster power transaction never completes
   from any runtime path [hardware-verified, baseline-delta table].

Answer to the task's question: **yes** — the v2000a driver path assumes a
SMU-side power-up that BC-250's NULL msg 0x8/0x9 handlers make impossible
from the host, so without the PSP-side release block (or a patched SMU
exposing a PowerUpVcn-class message), `vcn_v2_0_start` cannot reach its
PGFSM poll with a live domain. The residual unknowns are exactly the two
named in the verdicts: the svc #0x7B/0x7C/0x5E/0x5F handlers outside t28
and the upstream rejection site (0x11460 area).
