# Post-W11 boot-log history audit

Date: 2026-09-21 (Asia/Almaty). Scope: retained boot/programmer records only; no board reconnect, network contact, programmer command, or hardware operation.

## Conclusion

The saved-file timeline has one kernel log saved after the 2026-09-19 W11-labelled SPI readback: `evidence/runtime/20260919-w12-mode2/dmesg.txt` (mtime 03:43 +05 versus W11 readback mtime 02:42 +05). It reports BIOS DMI text `P5.00 05/03/2022`, but does **not** bind the boot to the W11 readback hash or identify the board by serial/revision. The W12 log records AMDGPU VCN initialization failure (`mmUVD_PGFSM_STATUS`, decoder ring `-110`, `vcn_v2_0` init failure), then continued systemd startup and an Ethernet link-up message. This is a GPU/VCN initialization failure in a Linux boot trace, not evidence of a BIOS boot failure or BIOS recovery.

No retained post-W11 boot log records a BIOS flash, CMOS clear/battery removal, DRAM training result, memory-training fallback, or a recovery operation. No W11-specific boot log exists in the inspected runtime inventory. The W9/W10 runtime captures predate the W11-labelled readback; their similar `P5.00` DMI strings do not identify their exact ROM. Present physical chip contents and executing BIOS remain unverified.

### BIOS flash and CMOS-clear evidence

- The 2026-09-19 `docs/research/2026-09-19-zero-day-confirmation.md` states that the W9-labelled candidate with hash `3c50bc9a…` was flashed and independently read back as W11. The saved readback bytes support the readback identity, but no W11-specific flashrom stdout/manifest was found in the bounded inventory. The same report's wording that the W10/W11 session booted that image is not corroborated by a W11-named runtime log; the exact W10 runtime log is saved before the W11 readback and the baseline identity report marks its image-to-log association inconclusive.
- No later-than-W11 BIOS/programmer write or readback appears in the inspected `evidence/programmer/reads/20260919/` set or the checked post-W11 action records. The 2026-09-20 FD-port action log states that its operation was an offline build with `hardware_written=false`; it records the latest chip status from prior evidence, not a new read. This is a bounded negative about retained records, not proof that nothing happened outside the saved project.
- No post-W11 boot log or checked post-W11 action record documents a CMOS clear or battery removal. The W9/W10 logs' `rtc_cmos ... setting system clock to 2021-01-01` lines predate the W11 readback and are not evidence that CMOS was cleared. W12's `systemd-journald ... Realtime clock jumped backwards relative to last journal entry` (line 2063) gives no cause and cannot be attributed to CMOS/RTC reset.

### DRAM training, fallback, and recovery

- The W12 log begins after early boot and contains no retained POST, DRAM training trace, trained memory-rate field, or memory-fallback status. The bounded search of its text for CMOS/battery/training/DRAM/MCLK/UCLK/FCLK/reset-reason terms produced no matches.
- W9/W10 kernel captures do not expose a DRAM training result either. `EDAC MC: Ver: 3.0.0` is only a subsystem version line. `Fallback order for Node 0: 0` is the Linux NUMA allocator policy; `Fence fallback timer expired on ring sdma0` is AMDGPU SDMA fence handling. Neither is DRAM training fallback. The W9/W10 previous-reset parity text and W10 `CF9` line are earlier captures and do not identify a memory-training cause.
- The separate 2026-09-16 T1 record (`docs/action-logs/2026-09-16-m0-window.md`) says a 1750-labelled request byte later reverted from `0x23` to `0xFF`/Auto; it is a different, pre-W11 native-base experiment. It does not establish post-W11 training fallback or a physical memory rate.
- W12 provides no evidence of a BIOS recovery, rollback flash, fallback image, or CMOS recovery. It shows the VCN block failing while systemd and network-link initialization continue. The project’s last later reachability status says the board was unreachable at the 2026-09-20 check (`docs/action-logs/2026-09-20-fd-v22-to-clv-port.md`); that status is not a boot log or a new chip read.

## Interpretation

1. **No exact W11 boot identity is established.** The W11 readback is the last saved chip snapshot, but the only later saved kernel log is W12-mode2, whose DMI product/version text is shared and whose partial capture lacks the image hash. Do not state “W11 BIOS booted” from this log.
2. **A later W12 Linux capture exists in saved-time order.** It records a serious VCN/GPU initialization failure, but sufficient later kernel/userspace activity that it is not a whole-boot halt in the retained trace. The trace does not say whether video/SSH/user workload succeeded.
3. **No post-W11 flash, CMOS clear, DRAM training fallback, or recovery event is documented in the bounded source set.** This is not an assertion about undocumented operator actions. The board’s present state remains unknown.
4. **Identity is limited.** The DMI string reports product/version text, not an exact ROM hash or physical PCB revision. `BC250-01` is the project target label; none of these runtime files gives a physical serial/revision.
