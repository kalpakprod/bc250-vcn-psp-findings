# R2 — +VDDCR_SOC BIOS control path: proven limitation

Date: 2026-09-23 (Asia/Almaty)
Task: Plane «BC250» issue #2 (R2) — find a verified BIOS path controlling +VDDCR_SOC (SoC actuator), or prove the limitation.
Status: **limitation proven** (static analysis + netlist classes; no hardware measurement in this pass).

## Verdict

There is no BIOS (or firmware) path to +VDDCR_SOC on this board revision. The requirement chain (BIOS item → variable consumer → SMU message → actuator → electrical receiver) is broken at every link:

1. **BIOS inventory contains no SoC voltage control.** The CBS/HII inventory exposes `VDDCR_VDD Voltage Offset` (`AmdSetup+0x6E6`, token `0x1364`), `VDDCR_GFX` offsets (`+0x6EA/+0x6EB`), and the fixed-voltage VCORE/GFX/MEMIO fields (`Setup+0x1C9..0x1D2`, staged to ISL69247/ISL95712 via the EC/SMBus path). Every `VDDCR_SOC` item in the inventory is telemetry slope/sign/magnitude calibration, not a setpoint. No direct immediate reader of tokens `0x1363/0x1364` exists in the bounded stock corpus audit (docs/research/2026-09-21-voltage-evidence-integration.md).
2. **The SMU message surface has no SoC-voltage message.** Full handler sweep of robin_5 queues 0/1/2/3/5 (all non-reserved entries, ~120 functions decompiled; see `evidence/firmware-audit/20260923-r2-svi-census/`): every voltage handler addresses exactly two domains. `q3 0x0F set_cpu_gpu_vid` dispatches kind 0 → `0x2bd80` (CPU wrapper) and kind 1 → `0x2bda4` (GFX wrapper); any other kind is rejected. The only `VddcrSoc`-named messages (`q0 0x11` QueryVddcrSocClock, `q3 0x42` SoC DPM value) address the SoC fabric **clock** domain, not voltage.
3. **The SVI2/VR12 actuator port commands two planes only.** The command register `SMN 0x0115A030` (= stored base `0x01159E00` + `0x230`) is written by exactly three helpers: selector byte `0x00` (`FUN_0002bdec`, CPU), `0x01` (`FUN_0002be40`, GFX), and one-time calibration `0x20` (`FUN_0002be18`). The base pointer slot `0x171a4` holds the only `0x01159E00` literal in the whole 262,400-byte image; direct literals of `0x0115A030`/`0x0115A000` do not occur (all access is base-relative). No third selector exists anywhere in the handler corpus.
4. **The selector state has two domains.** `_DAT_00017124` (base `0x13474`): domain 0 at `+0x00/+0x04/+0x0c/+0x14` (voltage float, VID, readback float, large offset) and domain 1 at `+0x20/+0x24/+0x2c/+0x30`; `+0x50/+0x54` are the two droop-calibration floats. All writers are CPU/GFX handlers (`0x0F/0x10/0x30/0x36/0x37/0x38/0x3B/0x3C/0x49/0x4A/0x4D/0x4E/0x4B/0x4C/0x9A`, q1 `0x10`).
5. **The board wires no SoC voltage receiver.** U25 (APU) SVI2 pins `APU_SVD/APU_SVT/APU_SVC` → series resistors PRA29/31/32 → `CORE_GFX_SVD/SVT/SVC` → PUA1 (ISL69247, a two-rail part feeding `APU_VDDCR_CORE_RUN`/`APU_VDDCR_GFX_RUN`). The ISL69247 PMBus (`CORE_GFX_PMSCL/PMSDA`) routes via PRA34/35 to `SMB0_CL/DA_ISO` (EC/Super-I/O SMBus). PUS1 (RT8237E, the +VDDCR_SOC regulator) has 11 pins, all analog (PG, OCSET, EN, FB, RF, LG, VCC, PHASE, HG, BST, GND) — no SVI, no PMBus, no EC pin. `SOC_EN` is hardware-sequenced (PCS3/PRS4/PRS19/PRS20). +VDDCR_SOC members: PLS1, PCS13–18, NSS1, U25 (32 pins), decoupling, `VTB_SOC` — no digital endpoint. The earlier 9-net audit already showed the SoC feedback is a fixed resistor divider with remote sense from U25 BC20/BD20 (docs/research/2026-09-23-soc-feedback-topology.md).

Consequence: even a custom DXE driver (this project's driver track) cannot reach the SoC rail: the SVI2 port on this board carries only planes 0/1 to the ISL69247, the EC SMBus reaches ISL69247/ISL95712 (VCORE/GFX/MEMIO) only, and PUS1 has no digital interface at all. Changing +VDDCR_SOC requires hardware work (FB divider resistors or a controller swap), out of BIOS scope.

Corollary (telemetry reclassification): the two SMU-table words 1275 and 912 (mV) captured 2026-09-13 at table offsets `0x50/0x54` are the two droop-calibration/domain floats of the CPU and GFX planes (state `+0x50/+0x54` region). They are not SoC measurements. The Linux driver label `Voltage[0]=VDDSOC` (cyan_skillfish_ppt.c) does not match this firmware's two-plane (CPU/GFX) layout; no SoC voltage telemetry exists in the robin_5 metrics path either.

## Census completeness bound (named honestly)

Ghidra's reference counter undercounts on this processor: `getReferencesTo(0x171a4)` returns one reference while three helpers demonstrably load the slot. The completeness argument therefore rests on three legs, not on reference counting: (a) every non-reserved mailbox handler in queues 0/1/2/3/5 was explicitly decompiled and inspected (sweep covers the full known_messages_robin5.txt surface); (b) the SVI base has a single literal storage in the whole image, so any access must load it, and every decompiled accessor belongs to the known helper cluster; (c) the physical cap: only two SVI planes are wired on this board, so a hypothetical unwitnessed third-selector write would still have no electrical receiver. A writer outside the mailbox surface (e.g., an init-time direct write) is not excluded by (a)+(b) alone but is capped by (c).

## Falsifiers / what would change the verdict

- A different board revision wiring PUS1 differently (this netlist is GenCAD r1.00, physical population unverified).
- An SMN/EC route to the SoC rail not present in this firmware revision (robin_5 / CLV 5.00) — e.g., a different BIOS with an SoC VRM controller.
- Hardware-only routes (FB divider change, controller swap) exist but are outside the BIOS track and outside this verdict's scope.

## Consequences for the plan

- `clv500-actuator-first` P2 sub-item «Для SoC отделить уставку от telemetry calibration…» — resolved as limitation: no SoC setpoint exists in firmware; no receiver exists on the board.
- P4's precondition «Сначала подтвердить управление SoC» — confirmed unachievable via BIOS. The SoC ≤1.15 V target cannot be set or verified through firmware on this board. Profile selection must proceed without an SoC-voltage step (operator decision required on whether to drop the SoC-voltage requirement or move it to a hardware-only track).
