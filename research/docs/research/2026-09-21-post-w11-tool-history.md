# Post-W11 hardware and tool history audit

Date: 2026-09-21 (Asia/Almaty). Scope is the saved action-log record from the 2026-09-19 W11-labelled readback through 2026-09-21. This is a records audit, not a board-state test.

## Conclusion

**The reviewed action logs contain no recorded successful post-W11 `flashrom`/programmer transaction, live BIOS/NVRAM operation, or read-only probe of BC250-01; no fresh present-state board capture is recorded.** The newest saved full-chip image remains the W11-labelled 2026-09-19 readback (`evidence/programmer/reads/20260919/postwrite-vcn-unlock-w11-v001.bin`, 16,777,216 bytes, SHA-256 `3c50bc9a65194b75ca805e6ed31c5778369de1fe8eca4600f44e15fae3b40fc3`). This is a last-saved image, not proof of the chip's present contents. Its exact contemporaneous flashrom stdout/manifest was not found in the bounded inventory. A historical W12-mode2 runtime log exists later in saved-file mtime order, but it is not a current capture or an exact W11-image boot identity; see the table below.

There were post-W11 **successful local/offline commands**, but they do not establish a BC-250 hardware event:

- The existing clock collector ran on the analysis workstation on 2026-09-20 and returned no target card (`cards=[]`; local `card1` device `0x1900` was skipped because the target ID is `0x13fe`).
- On 2026-09-21, `python3 scripts/probe_bc250_clocks_readonly.py --help` exited `0` but, because the script has no CLI parser, it executed its ordinary workstation collection path. It read local host/DRM metadata, found only device `0x1900`, and returned no target card. This was a host-only accidental probe, not a BC250 connection. Sensitive host values are intentionally not reproduced.
- `scripts/nvar_audit.py` successfully parsed NVAR fields from the **saved W11 image file**. That was an offline file read, not live NVRAM access.

A 2026-09-20 candidate-build log says the board was unreachable and records `100% loss`, but does not retain the exact network command, its process output, or exit status. Treat that as a historical log assertion of failed reachability, not as a verified board capture or as observed command-execution evidence. In a separate change-history record, an action log says the operator replied `да менял` (“yes, changed”); it does not identify what changed, when, or by which mechanism. That user report is not evidence of a specific flashrom/NVRAM/probe event, but it does mean the W11 image must not be treated as current without further identity evidence.

## Attempts and errors are not hardware events

The post-W11 logs preserve these local command/tool issues:

1. The baseline ROM ledger first named a nonexistent path, `evidence/programmer/reads/20260919/postwrite-vcn-unlock-w9-v001.bin`; the shell reported `No such file or directory`. The correct W9 readback was later hashed under `20260918`. The initial wrapper did not retain a numeric exit status. This was a local filename error, not a programmer command.
2. The NVRAM-ledger scratch setup with `rm -rf /tmp/bc250-baseline-nvram-work/reports` was rejected by the command runner before process creation; no command ran. A temporary selected-field wrapper later exited `1` with a Python `SyntaxError`; it did not modify the saved W11 image. The corrected `nvar_audit.py` run described above exited `0` against that saved file.
3. The clock script's `--help` invocation is the one exception to “no probe command”: it actually started and successfully read the local workstation path, despite being intended as a help check. Its successful exit is not a successful target-board probe.

No log found in this bounded interval documents a flashrom error, an attempted flashrom write, or a direct live NVRAM command after W11. This finding describes the retained action logs only; no inference is made about any action absent from them.
