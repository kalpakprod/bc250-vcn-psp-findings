## (c) Verdict

**Consistent: YES — our 512+gamescope+AAA failure is consistent with community + docs + upstream evidence, and expected at our config.**
The chat corpora contain zero exact flip-ENOMEM/SIGABRT quotes (E1-E2), so our crash is _novel to chat history_ — but the identical signature is documented in the local docs mirror as the 512MB scanout-pinning failure (E3) and on non-BC250 512MB-VRAM hardware upstream (E4), with the pin-ENOMEM→flip-fail mechanism confirmed across four more upstream sources (E5). The nearest chat precedent (whiteflower A1) is the same failure class: 512MB carveout + gamescope/mode transition + allocation failure, fixed only by a larger minimum split. Nothing in chat contradicts this: 512-correlated game failures were all fixed by bigger carveout, TTM raise, or zram→swap (`/tmp/uma512-T01.md:68`), and none shows a 512+gamescope+AAA success under our exact bundle.

**What explains "works for them": ranked config differences (every row sourced).**

1. **Minimum carveout size (decisive for THIS signature).** Scanout framebuffers must pin in the real minimum carve; GTT pages don't qualify — so 512MB + a filled device-local heap fails the gamescope flip while 4-6G survives. Docs: 6G resolved it, ttm.pages_limit does NOT help this failure (`/tmp/uma512-T12.md:70-72`). Chat: whiteflower 4G fix (A1); FF16 4G (A6); SM2 6G/8-8 (A8); Stellar 6G (A7); bezlitza 6G (A5). Discord doctrine agrees 512 is default but situational larger splits fix crashes (`/tmp/uma512-T08.md:12-30`).
2. **TTM ceiling raise (fixes a DIFFERENT crash class).** Default dynamic cap ~8-8.25G even at 512 (Oleksii msg 142188; mirror AL181-185 via `/tmp/uma512-T12.md:25-31`); exceeding it = instacrash/black-screen fixed by `ttm.pages_limit` 3145728 (12G) / 3959290 (~15G) / 3014656 (12G) / 3584000 (14G) (`/tmp/uma512-T02.md:31-37`; `/tmp/uma512-T04.md:21-25`; `/tmp/uma512-T09.md:25-76`; `/tmp/uma512-T12.md:35-51`). S2/S3 successes are this class — do NOT transfer to flip-pinning.
3. **Our GART is abnormally small (512M) vs every community success.** Our dmesg VRAM/BAR/GART all 512M (`/tmp/uma512-T14.md:10`); community GTT is 9-16G (Nekto 16384M msg 127548; Seol gttsize=14000 msg 1447751600650063893; big_trov texture-pool analysis msg 1475389967386546317; whiteflower "GTT ≥ 9G" msg 164768) via `/tmp/uma512-T07.md:33-43`; `/tmp/uma512-T09.md:27-61`; `/tmp/uma512-T05.md:26`. No community report runs 512M GART successfully.
4. **sg_display=-1 is entirely unvalidated.** Zero mentions in Telegram 38972 + digests + Discord tracks/raw/bulk + whiteflower's repo (fetched 2026-09-22, async-compute only) (`/tmp/uma512-T01.md:9,50-52`; `/tmp/uma512-T03.md:9-37`; `/tmp/uma512-T09.md:12-18`; `/tmp/uma512-T10.md:18-19`). Mirror documents only `=0` for kernels <6.10, unset on 6.10+ — no `-1` claim (`/tmp/uma512-T12.md:129-135`). Upstream AMD patch thread shows small-VRAM scanout placement (VRAM vs GTT) is explicitly special-cased and plausibly interacts with sg_display (`/tmp/uma512-T13.md:55-68`, snippet-only).
5. **Session type.** "512 works" reporters often run desktop/Plasma or per-game gamescope, not full BigPicture-in-gamescope; desktop changes the memory budget by ~1GB (msg 150418) and the flip path (`/tmp/uma512-T07.md:18-31,149-151`).
6. **Swap layout.** 512 successes co-bundle zram-off/zswap/swapfile (S15); ZRAM×512-dynamic conflict is independently documented with fixed-10/6 or 12/4 as fix (`/tmp/uma512-T12.md:83-97`). Our swap values were not in evidence (`/tmp/uma512-T07.md:147-148`).
7. **Game/settings load.** Same-box light-OK/heavy-fail pairs; FG/texture-pool/DX-version discipline (Spider-Man 2 FG-off msg 130740; Doom TDA texture-pool-min msg 127696; Arc Raiders DX11-only mid 1486736814604681387; big_trov pool<2048 msg 1475389967386546317) via `/tmp/uma512-T06.md:51-56`; `/tmp/uma512-T07.md:66-82`; `/tmp/uma512-T09.md:53-61`.
8. **ACBF build/proton recipe.** Our target is plain ACBF AppID 3751950 launch (`/tmp/uma512-T14.md:12-14`); chat "successes" are "новый black flag" of unknown build (S10) or Resynced-mod + LinUwUx proton + SVM/cpuid workaround (S12) — DRM/VM-detection stories, not VRAM stories (`/tmp/uma512-T08.md:162-165`).
9. **Stack edge.** Our kernel `7.2.6-1.2-bore-vcn` has zero other users in dump (bore hits are CachyOS flavors; 7.2.x hits are .0/.2/.3/.5, `/tmp/uma512-T03.md:77-80`); Mesa 26.2.3 has zero matches (26.2.1/.2 present, `/tmp/uma512-T03.md:81-82`); docs newest-tested is kernel 6.19.x / Mesa 25.3.x with 7.0-rc4 "do not use" (`/tmp/uma512-T12.md:145-149`); nearest stack is whiteflower Bazzite 44 / 7.2.0 / 26.2.1 msg 157204 (`/tmp/uma512-T01.md:33,77`); and our own evidence doubts system-Mesa-26.2.3 was even loaded (game pinned to /opt 26.2.0-rc3, `/tmp/uma512-T14.md:20`).

**Single most likely "works for them" answer:** they run a larger minimum carveout (4-6G) and/or never traverse the gamescope flip path under a filled 512MB device-local heap with a 512M GART — plus the usual TTM/swap/session/settings bundles. No reporter validates 512 + full-gamescope-session + AAA + sg_display=-1 + 512M GART.
