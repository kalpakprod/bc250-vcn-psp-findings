**Current solution:** keep asking different workers to inventory sources, histories, hashes, menus and outputs before choosing a BIOS.

**Climb 1 — what is that a way of doing?** It is a way of producing decision-grade evidence for a clock-control choice while preserving the saved 1800 request and source image.

**Climb 2 — what is that a way of doing?** It is a way of closing the causal chain from request to physical outcome, while keeping each intervention reversible until its result is independently observable.

**Fan at climb 1 (alternatives serving decision-grade evidence):**

- **Edge ledger, not another inventory (obvious, keep):** maintain one row per directed edge `Setup field -> token -> carrier -> consumer -> actuator -> unit/training -> observer`; attach an owner, exact input hash, current status, and a single result artifact. ## Options, outside view, and recommendation

- **A — Continue bounded offline consumer/actuator tracing (preferred next step):** cheap/reversible and directly targets the open causal edge; accept that it may end in a precise “opaque/unresolved” stop.
- **B — Hold unchanged/no candidate:** safest default if the next data-bearing edge cannot be bound; loses schedule but preserves hardware and source optionality.
- **C — Defer to a future authorized live experiment:** highest information value for actual application/physical clocks, but unavailable for this report and requires the full recovery/approval gate. Current installed BIOS identity is not required before the offline trace.

No defensible numeric base rate exists locally for a custom BC-250 BIOS setting to yield physical 1:1:1 or a stable latency change. The repeated serializer/HOB “PASS” checks update confidence in those byte-level facts only. They do not update evidence of physical clock acceptance. The weakest decision-quality element is meaningful actuator/observer information; spend the next effort there, not in another provenance pass.

Recommendation: keep the plain CLV source and `1800MHz` request unchanged, close the generic provider edge as a bounded negative, and direct the next accepted work only to an exact consumer/actuator or domain-specific observation edge; accept delay/no candidate as the trade-off for not guessing.

### Premortem and red team

If this reset fails, likely causes are: (1) stale or unreceived child briefs continue to generate unrelated outputs—mitigation: receipt + task sentinel + unique output path before accepting; (2) multiple workers repeat same source slice—mitigation: one owner per edge and a registry keyed by current run IDs; (3) a static record or GFX clock counter is relabelled as MCLK/UCLK/FCLK application—mitigation: name evidence layer and required unrun observer; (4) memory-unit or HOB semantics are inferred from numeric coincidence—mitigation: require caller argument/dataflow plus an independent definition; (5) SoC `1.15 V` is silently treated as safe—mitigation: exclude voltage changes and block hardware use absent a separate validated rail/limit and recovery decision.

Strongest case against the recommended offline-first route: only execution on the target can show what the closed firmware actually applies, and additional static tracing could be another expensive detour. However, no exact candidate/actuator is currently justified, the user has not authorized a current hardware action here, and current telemetry is not independent; a hardware-first trial would confound unknown semantics with unverified voltage/training/recovery. The dynamic route remains the decisive later acceptance test, not permission to skip the offline gates.
