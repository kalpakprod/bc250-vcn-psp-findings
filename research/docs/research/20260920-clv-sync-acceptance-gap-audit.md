# CLV 1:1 candidate versus physical-acceptance gap audit

> Audit 2026-09-27: the M6/17 September state below is historical within the selected inputs, not the latest/current board state. Later logs exist; none is a fresh liveness check. No recovery, flash or runtime operation is authorized by this summary.

## Conclusion

**Full physical `MCLK=UCLK=FCLK` acceptance cannot be established from offline evidence or without access to the exact target board.** The plan defines the release result as a hardware-verified applied/default profile: independently identified clocks/divider/crossing state, boot/Load-Defaults behavior, performance comparison, and stability. No offline decoder, image hash, parse, candidate build, or aliased software metric can substitute for those physical observations.

This does **not** mean live telemetry blocks offline development. The plan and D30 decision allow an explicitly experimental offline candidate after offline semantic/consumer gates close. Those gates are still **OPEN**, so the current blocker to a truthful 1:1 request artifact is offline semantics—not absence of a live capture.

## Safe operator test/recovery knowledge

- **No-flash offline action:** current safe next work is close the static consumer/semantic/default-precedence gates, then create an explicitly experimental offline transaction. No board telemetry needs to be collected first.
- **Read-only board baseline procedure:** the stock-capture runbook requires an operator-supplied authorized board session, confirmed target PCI ID and current baseline provenance; it suppresses `/proc/cmdline`, hostname and full journals at source, uses a 15 s timeout and recommends separate idle snapshots. It yields kernel-reported metrics only and explicitly labels synchronization INCONCLUSIVE.
- **Flash/recovery procedure if later approved:** current-target fresh full-chip reads (two matching reads), identify exact chip/board/memory and retain the exact recovery image/hash; board unpowered with programmer/3.3 V checks; exact candidate/target approval; built-in flash verification and an independent full readback/cmp before power-up; stop and recover on any mismatch. The old `read-a.bin`/CH347 route proves historical capability, not a current M6 rollback image.
- **DF1400 discriminator:** its runbook explicitly stops after request-retention readback if an independent physical DF measurement is unavailable. It must not be repurposed as a 1:1 proof.

## Existing decoder provenance / corrections checked once

The current `20260920-native-uclk-luna` report is an exact-byte serializer/INV-adapter trace (`AmdSetup+0x330 -> $INV 0x1204`); the independent review re-extracted the exact module from the pinned image and corrected the actual store address. It claims no final clock branch or 1:1 behavior. Its original “outside census”/reader-matrix wording was corrected to “unresolved within bounded static coverage,” not proven absent.

Already-recorded branch/decoder corrections that must not be revived:

- ABL1’s earlier generic “try the next token” description is superseded by the byte-backed status/gate/sentinel precedence trace; a non-`1` earlier gate is terminal, as is a final typed sentinel.
- A proposed universal ABL1 runtime base `0x60000` was falsified because a callable callback literal maps to ASCII under that base; `0x57100` is conditional coherence only, not a confirmed load/runtime base.
- ABL1’s selector TBB does **not** accept all IFR Memory Clock options: `0x26`, `0x27`, and `0xFF` route to invalid target `0x232A`; the helper at `0x64C8` remains opaque. The matching values of the other 20 entries are a table correlation, not physical MHz evidence.
- Prior serializer adjacency claims `+0x6A3→0x1332` were corrected by destination-pointer ownership to `+0x6A3→0x1331`; that is serializer-token identity only.

No new raw scan or decoder run was performed for this audit.
