# 10. Рантайм-рецепт разблокировки VCN (без прошивки флеша)

> **Историческая гипотеза, не инструкция к запуску.** Оригинал SHA-256 `0219dabc1b5475ccda04cea22961c21da884df63ce3f2bbfb811c4489e0b499a` сохранён в локальном архиве. Сам документ признаёт, что доставка команд PSP, наполнение реестра и эффект загрузки блоба не проверены на плате. Записи SMN и чтение VCN MMIO могут зависнуть; ничего здесь не разрешает выполнять опыт или прошивать BIOS. Текущие ограничения: [реестр пробелов](../../2026-09-27-autonomous-firmware-gaps.md).

Фаза C2. Авторизованный реверс собственного железа (AMD BC-250). Всё ниже — статический реверс TOS-контейнера сток-образа + открытые интерфейсы AMD; звенья, не доказанные статически, помечены явно.

## Суть канала

- Канал: x86 → C2P/SOS mailbox → супервизор PSP → TOS-диспатчер fn@0xBA98 (TOS-контейнер @0x984F00, код с +0x100).
- Команда = слово [r4] диспатчер-фрейма (0x78 байт), карта команд: `evidence/b1_emul2.txt`.
- Ключевые команды: 0x100B (токен), 0x100C (загрузка блоба), 0x1033 (применение), 0x100D (выгрузка слота).
- Доказано: гаскет/политика 0x24/0x45 из флеша подписаны RSA-2048 (kid 96EA) — шить кастом во флеш нельзя; путь ниже флеш не трогает вообще.

## Установленные механики (статически)

### Команда 0x100B — получение токена

- 0x100B → arm 0xC0C4 → fn@0x3528. Найдена свипом эмулятора `b1_emul2.py`.
- Аргументы диспатчера: r1 = указатель на буфер в общей памяти, r2 = размер буфера; требование size ≥ 0x140, иначе ошибка 0xFFFF300F.
- При первом вызове за бут (флаг-байт @0xE188C0 == 0) токен 0x20 байт выводится локально в RAM 0xE25814 через fn@0x5fa0 (HMAC-подобная функция над ключ-материалом @0xE17964/0xE179b2 и данными сообщения); svc-вызовов в fn@0x3528 нет.
- Каждый вызов копирует текущий токен @0xE25814 в буфер сообщения @+0x100 (0x20 байт) и пишет 0x40 в [buf+0x14].
- Следствие: токен per-boot НЕ выбирается нами — он выводится PSP и возвращается нам в ответе; читаем его из буфера по смещению +0x100.

### Команда 0x100C — загрузка блоба (fn@0x13468)

- Сообщение: слово0 = указатель на дескриптор {u32 источник; u32 ожидание-указатель; u32 тип}.
- Источник — стрим-дескриптор с 64-битным физическим адресом x86-памяти (+0x10/+0x14) и длиной (+0x18); fn@0x6800 читает блоб оттуда через svc 0x8b/0x6b (DMA-чтение супервизором).
- Принятый буфер: проверка заголовка [buf]==0x9000 и [buf+4]==0x7F; сам блоб начинается с buf+0x8000, заголовок блоба 0x100 байт, тело с +0x100 от начала блоба.
- memcmp#1: 0x20 байт вывода fn@0xd1fc (хеш) сравниваются с ожиданием ИЗ нашего сообщения — поставляем любые 0x20 байты, проходит всегда.
- memcmp#2: тело блоба [0:0x40] должно равняться {токен@0xE25814 || нули}. Токен — из шага 0x100B.
- RSA-хвост $PS1-блоба на этом пути НЕ проверяется.
- Успех: регистрация в 16-слотовой таблице @0xE4E538 (слот 8 байт: [0]=тип, [1]=runtime-id, [4]=указатель на принятый буфер); в дескриптор источника возвращается handle = индекс слота + 0x10 ([src+0x1C]).
- Нотификация супервизору: svc 0x90 (alloc 0x1000) → svc 0x88 → копия 0x1000 байт от начала блоба → svc 0x68 (сообщение супервизору с головой блоба) → svc 0x63 (free). Это вероятное звено, по которому супервизор парсит группы блоба и наполняет реестр @0xE5CBDC.

### Реестр и применение

- Реестр @0xE5CBDC: количество записей @+0x100; записи с +0x140 переменной длины {u32 тип; u32 число пар; пары {u32 адрес; u32 значение}}.
- fn@0x1167c(тип) читает реестр НАПРЯМУЮ (таблицу слотов @0xE4E538 он не использует). Весь контейнер содержит только две ссылки-литерала на 0xE5CBDC, обе — чтение; fn@0x13468 в область 0xE5CBxx не пишет.
- Заполняет реестр супервизор (on-die ROM, в образе отсутствует).
- Применение: команда 0x1033 → fn@0x20d4 (секвенсер, порядок групп 0x201→0x205→0x203→0x20A→0x20B→0x210) → fn@0x2178 на группу.
- fn@0x2178: типы 0x203/0x217 — прямой RAM-store `*addr = val`; все прочие (включая наши 0x201 и 0x210) — svc 0x7c(адрес, значение, 4), защищённая запись 4 байта.
- Команда 0xFFFF0001/0xFFFF0005 → fn@0xFE04 применяет все типы из того же реестра.

## Рецепт (последовательность для тестера)

### Шаг 0 — подготовка

- Собрать блоб: `python tools\psp-policy\c2_blob_builder.py <token-hex>` (после шага 1; для прогона всухую — плейсхолдер из нулей). Блоб: `evidence\fv_extract\c2_runtime_unlock_blob.bin`.
- Группы блоба (порядок пар критичен):
  - 0x201: 0x0900C234→0, 0x0900C914→0, 0x0900C930→0, 0x0900CB80→0, 0x0900C234→1 (commit после program), 0x0322011C→0x107FF.
  - 0x210: 0x03E810→6, 0x03E814→0x2544C382.
- Тело блоба начинается с 0x40 байт {токен || нули} (memcmp#2); валидация парсером — `c2_blob_builder.py` выводит разбор групп.

### Шаг 1 — получить токен

- Отправить команду 0x100B с буфером ≥ 0x140 байт в общей памяти.
- Прочитать 0x20 бай токена из ответа: буфер+0x100.

### Шаг 2 — собрать блоб с токеном

- Впитать токен в тело блоба: `python tools\psp-policy\c2_blob_builder.py <hex-токена>`.
- Посчитать 0x20-байтный «хеш» (любой, например SHA-256 тела) — это memcmp#1, поставляем его в дескрипторе.

### Шаг 3 — загрузить блоб (0x100C)

- Подготовить x86-буфер: [заголовок {u32 0x9000; u32 0x7F}] + паддинг до +0x8000 + блоб (заголовок 0x100 + тело). Выравнивание 4К.
- Сообщение 0x100C: слово0 = указатель на дескриптор {источник = 64-битный физадрес буфера + длина; ожидание = наш 0x20-байтный хеш; тип = байт типа блоба (кладётся в слот[0]; для применения через 0x1033 тип значения не имеет — реестр парсит супервизор)}.
- Успех: handle (слот+0x10) в дескрипторе; провал — чистая ошибка, состояние не портится.

### Шаг 4 — применить (0x1033)

- Отправить команду 0x1033.
- Предсказанный эффект: пары 0x201 → svc 0x7c(...) для VCN-хвоста гаскета (program→commit) и 0x0322011C→0x107FF; пары 0x210 → svc 0x7c(0x0003E810, 6, 4) и svc 0x7c(0x0003E814, 0x2544C382, 4).
- Порядок: секвенсер применяет 0x201 раньше 0x210 — как требуется (сначала program/commit гаскета, потом 0x210).

### Шаг 5 — верификация на x86

- Прочитать SMN/NBIO: 0x0900C234 (должен стать 1), 0x0900CB80 (0), 0x0900C910/914/930.
- Прочитать VCN MMIO-лестницу через BAR5 (NBIO SMN-порт 0x38/0x3C): UVD_VERSION и соседние регистры не должны быть 0xFFFFFFFF.
- VCN-сегменты включены → дальше стандартный bring-up (домен 6, VCLK/DCLK, navi10_vcn.bin) по доке 07/08.

### Транспорт x86→PSP (из открытых источников AMD, сверено с keshas_amdbc250_psp.c)

- C2P-регистры на BAR5 (MP0, байтовые офсеты): C2PMSG_35 @0x5818C (команда; bit31 = завершение, поллинг ~2с), C2PMSG_36 @0x58190 / C2PMSG_37 @0x58194 (аргумент / физадрес lo/hi), C2PMSG_64 @0x58200 (bit31 = TOS ready), C2PMSG_67 @0x5820C (ring WPTR), C2PMSG_69/70/71 @0x58214/18/1C (адрес ring lo/hi и размер), C2PMSG_81 @0x58244 (SOS-статус, bit31 = alive).
- Блоб передаётся физадресом 4К-выровненного x86-буфера (page_to_phys через /proc/self/pagemap); PSP забирает его сам (DMA).
- Ответ/поллинг: bit31 C2PMSG_35; данные ответа (токен) пишутся в тот же переданный буфер.
- Кодирование команд уровня GFX (libgv_amdgv_psp_gfx_if.h): LOAD_IP_FW = 0x06 | (FwType<<16); типы: 13=VCN, 61=DFC, 67=REG_ACCESS_WHITELIST, 0x4B=гаскет.

## Риски

- Персистентность: всё живёт до перезагрузки/power-gate PSP; холодный бут восстанавливает сток-гаскет.
- Повторное применение 0x1033: пары 0x201 идемпотентны по значениям (0→1 commit), повтор не должен ломать; 0x210 — константы, тоже идемпотентно.
- Конфликт со сток-гаскетом: сток применён при загрузке раньше; наш 0x201 перезапишет его пары для адресов VCN-хвоста — остальные банки стока не трогаем (в блобе только хвост + 0x0322011C).
- 0x0900CB80=0 снимает lock-регистр: повторный program/commit VCN-банка станет возможен и для других агентов — принять как осознанное решение.
- Провал загрузки — чистая ошибка return-code, слот не занимается; занятые 16 слотов освобождаются командой 0x100D (handle 0x10..0x1F).

## Недоказанные звенья (требуют проверки на железе)

- Связь «слот → реестр»: супервизор (on-die) не в образе; статически доказан только канал нотификации svc 0x68 с головой блоба и факт, что контейнер сам реестр не пишет. Проверка: после 0x100C послать 0x1033 и смотреть эффект; если эффекта нет — реестр из слотов не восстановлен, канала нет.
- Формат тела для супервизорного парсера: тело начинается с токена (0x40 байт), глобального слова-счётчика групп в flash-формате ($PS1) там нет; наш билдер кладёт записи групп сразу с body+0x40. Если супервизор ждёт счётчик в body[0] (flash-раскладка) — нужно, чтобы токен[0:4] == числу групп; зонд: вариант `--layout count-then-entries`.
- Точная x86-видимая кодировка TOS-команд 0x100B/0x100C/0x1033: с этой платы документированы только бутлодер-команды (0x06|FwType<<16, 0x10000000) и LOAD_IP_FW; диспатчер-фреймы (0x78 байт) доставляет супервизор из C2P-стрима/ring. Какое поле C2P становится словом [r4] — не доказано; кандидат — ring-команды GFX_CMD_ID_INVOKE_CMD / поле команды C2PMSG_35.
- Требование заголовка {0x9000, 0x7F} и окно +0x8000: восстановлены из fn@0x13468; фактическая раскладка супервизорного окна общей памяти — подтвердить на железе (первые 0x8000 байт переданного буфера).
- Токен: не выбран нами, а выведен и возвращён в ответе — вывод основан на дизасме fn@0x3528 (копия 0xE25814 → buf+0x100); подтверждение — прочитать непулевой токен из ответа 0x100B.
- Производная fn@0xd1fc: memcmp#1 сравнивает её вывод с нашим ожиданием — содержимое не проверяется, но если fn@0xd1fc падает на неподписанном блобе, загрузка не дойдёт до memcmp#2; тестом подтвердить, что проходит.
