# Baseline board boot, training, and kernel evidence ledger

Date: 2026-09-21. Scope: retained evidence only; no board reconnect or hardware access.

## Conclusion

The latest **booted** Linux captures in the retained runtime folder are dated by their folder/host mtime 2026-09-19; their SMBIOS/DMI text reports `BIOS P5.00 05/03/2022`. That is a firmware-reported product/version string, not an exact ROM identity: the W9/S9, W10, W11 labels refer to different image/readback records, and the existing identity reconciliation explicitly says the W10-to-CPU-log link is not established and the W9-labelled candidate is not the original W9 readback.

The latest recorded programmer image readback is the W11-labelled capture from 2026-09-19. The last status report says the board was unreachable at the 2026-09-20 check; the 2026-09-21 ROM ledger does not perform a new read. Therefore neither the **present physical chip contents** nor a booted BIOS/DMI string after the W11 readback is freshly confirmed.

No 2026-09-19 Linux log records DRAM training, a memory-training retry, MCLK/UCLK/FCLK, or a memory clock rate. The only preserved OC boot discriminator is older: the 2026-09-16 single-byte 1750 MHz NVRAM pin booted to Linux, but firmware restored the byte from `0x23` to `0xFF` (Auto); why it reverted is unresolved. This is evidence of request reversion, not evidence that training failed or that a lower physical memory clock was selected.

## What “fallback,” “clock,” and “training” mean in these records

- **Actual stored-request fallback/reversion:** only the T1 comparison establishes a user memory-clock request byte being restored to Auto. The cause is explicitly unresolved. There is no POST code, serial trace, training log, or contemporaneous clock read that distinguishes the candidate causes.
- **Not memory fallback:** Linux prints `Fallback order for Node 0: 0` (NUMA allocator policy) and AMDGPU prints `Fence fallback timer expired on ring sdma0` (GPU DMA fence handling). Neither says the DRAM trained at a lower rate.
- **Memory-training visibility:** the 2026-09-19 dmesg captures report SMBIOS “Memory slots populated: 16/16” but no actual memory speed or training outcome. Their EDAC lines announce `EDAC MC: Ver: 3.0.0`; no correctable/uncorrectable memory error line was found. This does not prove that pre-OS training had no fallback; those logs are OS-side and start after training.
- **Clock visibility:** W9/W10 dmesg TSC lines report about `3194 MHz`, which is a CPU time-source calibration, not MCLK. W10 `cpuinfo.txt` includes a sampled `cpu MHz: 800.000`, also CPU-side. The 2026-09-12 `pp_dpm_mclk: 450` is an older driver-reported value, not a physical MCLK measurement. None of the audited boot logs establishes MCLK:UCLK:FCLK or physical 1:1:1.
- **Kernel errors:** the recurring ACPI `_PR.C000`–`_PR.C00B` lookup errors and AMDGPU `Failed to clear hpd(rx)` messages are recorded, but no source connects them to memory training. W12’s `-110` is the VCN decoder/hardware initialization path.

## Current versus historical

1. **Historical boot/runtime evidence:** the P5.00 DMI string, 450 MHz kernel-reported MCLK, the T1 request reversion, W10 8-core output, and W12 VCN timeout belong to dated, distinct observations/firmware labels. They must not be merged into one simultaneously active configuration.
2. **Last confirmed chip image:** the W11-labelled 2026-09-19 programmer readback. This is not a fresh 2026-09-21 chip read and is not itself proof of a successful W11 boot.
3. **Current hardware/runtime state:** unverified. The last retained reachability report is “unreachable” at the 2026-09-20 check; no board reconnect was performed for this audit.
4. **Current user memory request/application:** no audited boot log proves a live CLV NVRAM request of 1800 MHz, a trained 1800 MHz state, a physical MCLK/UCLK/FCLK value, or the BIOS revision currently executing. Those require a fresh authorized identity/NVRAM/boot capture; this audit does not perform it.

## Remaining uncertainty

- The present physical chip image, PCB/revision, and executing BIOS identity have not been refreshed since the last recorded readback/status.
- No retained exact-board pre-OS training/POST diagnostic, training log, or memory-speed field is linked to the W9/W10/W11 boot records.
- No current NVRAM readback confirms whether the saved 1800 MHz request is present; no independent physical clock counters confirm MCLK/UCLK/FCLK.
- A future authorized read-only capture can settle identity and saved fields; a separate post-boot measurement must use independent, domain-mapped clocks to establish physical ratios. No hardware operation was performed here.
