## v003e ROOT-CAUSE MECHANISM (byte-verified, no inference past bytes)

The injected Bc250VcnUnlockDxe.ffs is a type-0x07 boot-service driver
whose body = ONE PE32 section + ONE GUID-defined section. There is NO
DEPEX section (0x13) in the FFS (byte scan: 0x02/0x10 sections present;
0x13/0x15/0x17 hits are in-section data, not section headers). With no
Depex, DxeCore dispatches the driver in the earliest phase-appropriate
pool, BEFORE the NBIO/PCI host bridge is fully mapped by AGESA. The
driver's EntryPoint runs VcnEnableSequence() -> SmuAlive() -> the FIRST
PciSegmentWrite32 to the SMN pair 0xB8/0xBC. That PCI-config write to a
not-yet-ready register is the early-init hang: PSP reached the first
green blink, DXE started, the injected driver poked unmapped hardware,
the SoC stalled before the second blink and before LAN/PHY bring-up.

Conclusion (locked in the log): driver-in-DXE is the wrong carrier for
this payload. The VCN mechanism (0x28/0x29 write pair + route-B replay)
is unchanged and OVMF-validated; it must run AFTER full init: the
already-built no-Shell boot app Bc250VcnProbe4.efi (reads/replays after
the platform is live), or host-side, not inside the BIOS volume.

## v004 POSTMORTEM — ROOT CAUSE (byte-proven, hardware-class)

The hang is NOT the driver and NOT its dispatch timing. It is the capsule
LZMA-alone header at 0xAE00A8:

- working pre-dump: `5d 00000001 10d04300 00000000` (explicit 0x43D010)
- v004: `5d 00000001 ffffffff ffffffff` (UNKNOWN size)

CPython lzma.compress(FORMAT_ALONE) emits unknown size. The board's PEI
capsule decoder rejects unknown-size streams, so the DXE volume never
decompresses and the board stalls after the first blink, BEFORE any DXE
driver runs. This is exactly why v003e and v004 behave identically.

This repeats the hardware-proven D5-D7 defect verbatim (D8 verdict
2026-09-12: restoring the explicit decoded length made the same candidate
boot). Supporting evidence that the driver is innocent at this stage: D10R
proved an immediate first-DXE SMN/Q3 touch boot-safe (Linux + Q3 alive).

Second-order finding: DEPEX TRUE is a scheduling no-op vs no-DEPEX (PI
spec: missing DEPEX == TRUE). The v003e->v004 "fix" could never have
changed dispatch order. The real dispatch question (early-DXE VCN writes
vs ReadyToBoot, D11 vs D12 classes) only becomes reachable AFTER the LZMA
fix lets DXE load at all.

Gate gap: preflight passed v004 9/9 GO because python-lzma tolerates
unknown size. Added G10 lzma_explicit_size (candidate outsize explicit and
equal to the stream length, params equal to base). v004 now scores NO-GO
on G10 alone; this is a strengthening gate addition, reason stated here.

## RE: ROUTE-B REGISTER OWNERSHIP MAP (2026-09-24, static)

Route B replays the TAIL of the SMU firmware's own 0x1B-handler body
(FUN_0002A184) from the host side. Target ownership (runbook + decompile):

- 0x0000CCB8 bitmap: SMU's own SRAM. SMU reads bit 6 only in the 0x2B0F4
  tail, which never runs on this board -> effectively inert. LOWEST risk.
- 0x0115A2xx gate modes + 0x0115F6xx ctl + 0x0115F8xx PLL/power: SMU SRAM
  space the SMU firmware itself sequences during boot (FUN_00024594 programs
  0x0115F8xx from the plan; FUN_00024878 is a second writer to 0x0115F600).
  Shared live ownership with a running microcontroller -> race. HIGHEST risk
  for the gate-mode group (R1-R6), HIGH for PLL enable/trigger (R8-R10).
- 0x0100Bxxx enable block: MMIO-ish block, likely inert until consumed.
  LOWER risk (inference).
- 0x0220FE00/0x01D80600 gates: skipped in v1 (read safety unproven).

Mechanism behind the D11/D12 class: host writes race the SMU's own boot
sequencing. Later dispatch = SMU boot work more complete = less race. This
is the mechanistic basis for the append (v007/v008) then ReadyToBoot (v009
if needed) ladder. If v008 hangs, bisect writes in risk order (gate modes
first), D13-D19 method. Ranking above is inference, not evidence.
