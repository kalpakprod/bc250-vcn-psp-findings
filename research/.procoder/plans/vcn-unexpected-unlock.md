## Connected groups

Host driver -> PSP request/loader -> gate/authorization -> SMU domain power -> fabric/NBIF route -> VCN firmware execution -> rings -> codec. Это дерево рабочих гипотез, а не доказанная строгая последовательность всех стадий. Отдельно учитывать единицы адресов и транспорт: register index, byte offset, SMN address, mapped firmware window не взаимозаменяемы.

## Варианты и минимальные проверки

### O1. «Включить не VCN, а право до него дойти» — приоритет 1

Гипотеза: проблема в маршруте/инициаторе, а не в питании. Не повтор старого NBIO sweep: нужен конкретный consumer поля маршрута.

Первый тест офлайн: для одного VCN регистра и одного известного GC-контроля восстановить выражение адреса по реальному коду каждого использованного транспорта. Явно учесть умножение индекса на 4, segment base, маскирование и окно. Затем связать VCN_SEG 0x03E810 с реальным потребителем/записью, а не объявлять значение donor=6 универсальным рецептом.

Выход: таблица {source expression, units, base, transport, effective address, known observation}, затем один доказанный маршрутный selector. Продолжать только если обнаружено различие разрешений/маршрута или ошибка вычисления адреса. Если адреса согласованы и consumer не найден в ограниченном наборе известных модулей, гипотеза остаётся неподтверждённой, никаких live записей.

Потенциальный unlock: изменить только доказанное поле маршрутизации для нужного инициатора. До подтверждения семантики ни 0x03E810=6, ни чтение 0x7fec не считаются безопасными.

### O2. «Пусть штатная прошивка сама сделает запрещённую работу» — приоритет 2

Гипотеза: VCN блокируется по контексту запроса, хотя общий post-load путь достижим из другого разрешённого штатного пути.

Первый тест офлайн: от check E121D8 и gate E18B70 построить ограниченный граф producers -> request validation -> loader -> reset writes. Сопоставить VCN и один реально существующий разрешённый тип запроса. Искать общий callback и условия, не перебирать mailbox на плате и не переименовывать VCN blob в чужой тип.

Выход: конкретный общий basic block и предикаты достижимости. Если все пути повторно проверяют тот же запрет или общего пути нет, закрыть эту ветку в исследованной области. Если путь есть, сначала контролируемое выполнение/trace без hardware IO, с остановкой на неизвестном service.

Потенциальный unlock: штатный порядок инициализации/корректный контекст вместо патча signed-кода. Наличие такого контекста пока не установлено. Privilege exploit или отключение authentication не являются условием этого плана.

### O3. «Разбудить соседа, а не VCN» — приоритет 3, слабее первых двух

Гипотеза: штатная инициализация другого клиента открывает общий участок fabric/reset/clock, пропущенный в VCN пути.

Первый тест офлайн: декодировать FUN_0001dd74 с точными типами, значениями записей и преобразованием адреса. Разделить глобальную housekeeping-функцию и VCN-специфический эффект. Сравнить только найденные call sites с реальным соседним клиентом в той же прошивке. JPEG/другой media-клиент допустим как кандидат лишь после подтверждения общего ресурса, не на основании названия.

Выход: пересечение конкретных write sets и один подтверждённый общий ресурс. Если функция является clear/reset без доказанного release, снять ярлык unlock. Без общего ресурса ветка закрывается. Репликация всей таблицы и прямой вызов функции на плате исключены.

Потенциальный unlock: штатная инициализация владельца общего ресурса до VCN. Это не перенос чисел от работающей 780M.

### O4. «Ловить повторное запирание, а не искать открывание» — резерв

Гипотеза: ранняя стадия открывает доступ, следующая его закрывает. Объединить статические write-xrefs одного уже подтверждённого selector по PEI/DXE/PSP/SMU. Первый результат должен показать две противоположные записи И их порядок. Без этого нет основания для раннего UEFI-патча. Возможный unlock: устранить позднюю перезапись в модифицируемой policy, а не усиливать раннюю запись. Подписанные области не менять. Hardware trace потребует отдельного плана и наблюдаемого канала.

### O5. «Вычесть запрет из двух прошивок» — резерв

Гипотеза: различие VCN определяется маленькой policy/procedure, а не всей донорской платформой. Сравнить homologous function и её входы в имеющихся P3/P5/CLV/4700S артефактах, без новых cross-flash. P3 нельзя называть working VCN donor. Подтверждённая работающая reference того же поколения усилит вывод, сейчас её нет. Выход: одно смысловое отличие с потребителем и ожидаемым эффектом. Масса различий или различная ABI без локализации = остановка. Возможный unlock: минимальная policy-правка только после причинного подтверждения и проверки подписанного диапазона.

### O6. «Запросить один кадр вместо чтения сотни регистров» — резерв, НЕ новая идея

Функциональный decode уже предлагался в памяти. Включён как конечный oracle, не как творческое открытие. Предусловие: доказано, что текущий driver-path не повторяет известный hard-hang при hw_init, либо пользователь отдельно принимает этот риск. Подготовить маленький фиксированный поток, software reference, требование аппаратного устройства без fallback. Успех: выполненные аппаратные задания/счётчики и корректные кадры, а не только ffmpeg exit0. Не запускать сейчас.

Альтернативы: ничего не менять и оставить software decode, или отложить аппаратную часть до нового наблюдаемого канала/совместимой working reference. Это безопасные варианты остановки, не выполненная разблокировка.

## Controls, наблюдение, rollback

Offline: исходный CLV read-only по дисциплине, hash до/после при запуске экспериментов. Если нужен harness: actual code, явные входы, invalid-request/known-client controls, trace writes вместо IO. Неизвестные MMIO/service не заменять нулями. Для любых будущих изменений — original, modified, reconstructing diff, literal baseline/modified/rollback evidence и executable rollback. Сейчас firmware не модифицируется, эти роли не создаются фиктивно.

Hardware: ни SSH timeout, ни trap wrapper не гарантируют остановку зависшего SoC. Cold power cycle — операторское восстановление, не автоматический watchdog. Перед flash отдельно полный dump, подтверждённый recovery, точное согласие на образ и последующий cold-boot/readback. Runtime rollback не восстанавливает испорченную SPI.

## Premortem и критерии остановки

1. Снова повесили плату «безопасным чтением»: запрет sweep и аппаратного IO в P1-P3, известные wedge-классы остаются запретами до нового согласования.
2. Нашли красивую историю вместо причины: каждый вывод имеет instruction/input/output anchor. «Нет caller» не превращать в «никогда не вызывается», all-ones не превращать в доказанный fuse/software lock.
3. Подменили адреса/поколения: O1 до записей, сохранять units и base, 780M не источник готовых register values для BC250.
4. Потратили ещё неделю на знакомые данные: не повторять APCB-only, 4700S cross-flash, bit17, bulk clamp reads и generic feature scan без нового discriminator.

Stop: нет нового различающего факта за ограниченный проход, неизвестный MMIO/service в исполнении, нарушение области подписи, необходимость нового аппаратного действия без согласования. Результат честно INCONCLUSIVE/BLOCKED, не unlocked.

## Open questions и decision log

Блокируют hardware: точный актуальный driver/boot state после последнего wedge, transport address semantics, последовательность и значения проверяемой записи, точное согласие пользователя. Не блокируют этот офлайн-план: фото платы, новая прошивка на плате, обещание успеха.

Рекомендация автора, не выбор пользователя: P1 -> P2 -> P3. Принимаем, что необычная идея может быть отвергнута до железа, ради меньшего числа непрозрачных зависаний. Пользователь запросил только план. Стадия review: текущий статус поправлен по журналу ошибки, ни одна гипотеза ещё не прошла новый эксперимент.
